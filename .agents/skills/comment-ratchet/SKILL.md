# コメント予算の ratchet 返済

長いコメントを「1 回で全部直す」のではなく、**検出器 → 予算 → バッチ返済 → 予算引き下げ**の
サイクルで減らす。件数で進み具合が分かる。

## 何を用意するか

返済を始める前に、対象プロジェクトへ次の 4 つを置く（既存の検査に合わせてパスを決める）。

| 役割 | 置き場所の例 |
|---|---|
| 検出器 | `scripts/comment-check.mjs` |
| 検査のテスト | `test/comment-check.test.*` |
| 予算の記述 | 規約（`AGENTS.md` など）と検証手順の docs |
| CI への組み込み | `package.json` の check 連鎖、または CI の job |

### 検出器の要件

- 対象はコメントを規約で縛りたいディレクトリだけ（最初は 1 つに絞る）。
- 数えるのは**本文が 3 行以上**のコメント。`//` の連続は 1 つ、空行は数えない。
- 文字列・テンプレート・正規表現の中の `//`、ディレクティブ（`// oxlint-*` など）と `///` は
  数えない（パーサか字句走査が要る）。
- `--list` で `file:line` と行数・字数を出す。これが返済対象の一覧になる。
- 予算（`LONG_COMMENT_BUDGET` のような定数）を持ち、**超過したら exit 1**。
  下回ったら「予算を N に下げられる」を stderr に出す（下方向の追従は人手で行う）。
- 予算はコード内の定数に置く。設定ファイルに置くと、下げ忘れに気づきにくい。
- 行数とは別に、**規約違反も exit 1** にする。少なくとも、JSX の子に置いた `/**`
  （コメントではなく文字として描画される）と、関数の中・属性の位置に置いた `/**`
  （`/**` は宣言の JSDoc にだけ使う）を検出する。JSX をパースせずに行で判定するなら、
  前者は「直前が `>` `}` `)` で、次が子要素」（JSX を書く拡張子だけ）、後者は「次が
  `return` / `useX(` / `(` / `{` / `<` / 属性の代入」のような形になる。

## コメントの書き方

- **1〜2 行**。3 行以上は docs へ移す（コードには索引だけ残す）。
- 残すのは**罠と契約**（「こうすると壊れる」「ここが正」「順序が決まっている」）。
  手順の説明（What / How）はコードを読めば分かるので削る。
- `/** */` は**宣言の JSDoc にだけ**使う。関数の中・属性の位置・式の位置は `//`。
- JSX を書く言語では、**JSX の子は `{/* */}`**。
- 同じ理由をコードと docs に二重に書かない。読む人がその module の外にもいるなら docs。
- Issue / PR 番号はコメントに残さない（経緯は履歴が持つ）。
- 予算を上げる・検査の除外を足すのは、レビューで合意した時だけ。

## 1 サイクル

### 1. 実測する

```bash
cd <project>
node scripts/comment-check.mjs          # ok (N 件 / M 行、予算 N 件)
node scripts/comment-check.mjs --list   # file:line の一覧
```

`--list` の出力をバッチ分だけ切り出す。1 ファイルあたりの件数が減ってきたら、
バッチのファイル数を増やす（1 PR のレビューが重くならない範囲で、8〜12 が目安）。

### 2. 書き換える

対象ファイルの 3 行以上のコメントを 1〜2 行へ。**元の罠・契約・順序を 1 つも落とさない**。
落とす説明が docs に無いなら、1 句だけ戻すか docs へ移す。

### 3. 予算を実測まで下げる

同じ PR で予算を実測値へ下げる。下げ忘れると次のバッチで「まだ余裕がある」と誤解する。
予算を**コードの定数と docs / 規約の両方**に書いているなら、同じ PR で両方直す
（docs 側は検査されないので、片方だけ直すと古い数字が残る）。

### 4. 差分がコメントだけか確認する

```bash
git diff --stat
# 対象ソースを 1 ファイルずつ。コメント行の増減だけなら出力は空
git diff -U0 -- <file> | grep -E "^[+-]" | grep -vE "^[+-]{3}" | grep -vE "^[+-][[:space:]]*(//|/\*|\*|\{/\*)"
# 書き換えで // が /** に化けていないか
git diff -U0 -- <file> | grep -E "^\+[[:space:]]+/\*\*"
```

空行の増減は `-` / `+` として出るので、置換で食っていないかここで見る。フィルタは行の
先頭だけを見る heuristic なので、`*` で始まるコード行（例: `+ * mult`）や文字列の中の
`//` は見えない（`/**` 化は 2 本目の grep で見る）。怪しいときは `git diff` をそのまま読む。

### 5. 検証する

```bash
node scripts/comment-check.mjs
node scripts/docs-check.mjs        # docs を触ったとき
npx <formatter> --check <changed files>
npx <test runner> <既存の test コマンドと同じ形>
```

全体の check（lint / typecheck / test / build）は CI に任せる。手元で回すと遅い。

### 6. PR を出す

本文に「実測 → 予算」「対象ファイルと件数」「検証コマンドの出力」を書く。
**数字はコマンドの出力をそのまま貼る**（手で書き換えると必ずずれる）。
本文の節はリポジトリのテンプレートに従う（解決する Issue が無ければ、その行は削る）。

### 7. レビュー → 修正 → マージ

- レビューは人間か、別のエージェントに頼む（Herdr 環境なら `herdr` skill）。
- LGTM でも nit が付く。**契約が消えていないか**の指摘が多いので、
  「docs に無い契約を消した」系は 1 句戻すか docs へ移してから再依頼する。
- **レビュー済みの head を控えておく**。直したら、再レビューで LGTM が出た時点で控え直す。
- CI が終わるのを待ってから squash merge する。base branch が required checks を
  要求している場合、待たずに投げると `the base branch policy prohibits the merge` で
  弾かれる（`--auto` は使わない）。

```bash
gh pr checks <n> --watch              # 終わるまで待つ
[ "$(gh pr view <n> --json isDraft -q .isDraft)" = true ] && gh pr ready <n>
gh pr merge <n> --squash --match-head-commit <レビュー済みの head SHA>
```

`--match-head-commit` は LGTM 時点の SHA を渡す。マージ直前に取り直すと、
レビュー後に head が変わっていても気づけない。

### 8. 次へ

```bash
git fetch origin
git switch -c <branch> origin/<base>
```

1 に戻る。進捗（`N → 0` など）は各 PR の本文と最後の報告に書く。

## 失敗しやすい点

- **JSX の子の `/**` は描画される。** 型チェックもコメント件数の検査も通るので、検出器の
  規約違反チェックで弾く。
- **行番号で置換すると空行を食う。** 1 箇所直すと後ろがずれ、次の置換が別の行に当たる。
  直す前に base からファイルを取り直し、テキスト一致で置換する。
- **書き換えで `//` が `/**` に化けることがある。** step 4 の 2 本目の grep で見る。
- **docs に無い契約を消すと、コードからも docs からも辿れなくなる。** 短縮は
  「契約を残して手順を削る」であって「説明を消す」ではない。

## 報告の形

```text
[#123](URL) をマージしました。進捗 N → 0（M PR、予算 0）。
残り: 対象外のディレクトリ（掃除後に検査へ追加）。
```
