## アーキテクチャの決定

設計判断は `docs/adr/` に従う。ADR に書くのは、コードから読み取れず、崩すと影響が広い判断だけにする。

- 書く: 技術スタック、データの持ち方と永続化、外部（公式サイト・マスタ JSON・NET）との連携方式とその前提、公開範囲とプライバシー
- 書かない: 計算式やデータ形式の仕様（docs/domain.md）、画面の見た目と挙動、手順（README / poc/README）。コミット・テスト・コードコメントに書く

ファイルは `docs/adr/` 配下の `<topic>.md`（小文字 kebab-case）で、番号を振らない。同じ論点は同じファイルにまとめる。判断が変わったら、そのファイルを現在の判断に書き換える。やめた判断はファイルごと消す（経緯は git に残る）。参照は docs/adr/ 配下のトピック名のパスで行い、番号で参照しない。

- `accepted`: 現在有効。実装はこれに従う
- `proposed`: 検討中。前提にしない

Accepted ADR とタスクが衝突する場合は、迂回実装で無理に両立させない。作業を止めて衝突を報告し、タスクと ADR のどちらを見直すか判断を仰ぐ。
