# RATING 分析スキル化の整理メモ（壁打ち用）

> ステータス: アイデア段階（壁打ち用・決定事項なし）。
> 「RATING 分析・提案」を将来エージェントスキル化するための要件メモ。
> 計算自体は PoC で自動化済み（`poc/run.py`・`poc/rating_core.py`）なので、スキルは
> **「既存コードの呼び出し方 + 分析・提案ロジックの整理」** を担うものとして考える。
> 表示側のデザインは [gui-design-spec.md](gui-design-spec.md) を参照。
> 本メモの数値はすべてダミー。実スコアは書かない（[conventions.md](conventions.md)『プライバシー（個人データの非記載）』）。

## 1. スキルが担う質問（想定される聞き方の例）

- 現在地・目標型: 「虹レまであとどれくらい？」「次の色まで残り何ポイント？」
- 改善提案型: 「何を伸ばせばいい？」「効率のいい鍛え方は？」
- シミュレーション型: 「この曲を SSS 出したら RATING いくつ増える？」「ベスト枠の底上げであとどこまで必要？」
- 構造把握型: 「これ以上伸びない譜面はどれ？」「伸びしろが一番大きい譜面は？」
- 比較型: 「新曲枠とベスト枠、どっちを鍛えるのが効く？」
- 指定曲リスト型: 「直近で狙えそうなのはこのリストの中だとどれ？」（入力パターン B・3 節）

## 2. 実行フローの段階分け

| 段階 | やること | 使う既存コード / データ |
| --- | --- | --- |
| 0. 前提確認 | 入力データ（スコア JSON 等）と計算済み CSV の所在・鮮度を確認 | `data/` 配下（Git 対象外）の実データ一式 |
| 1. 計算 | 未計算 or 古ければ再計算 | `python3 poc/run.py <入力> <出力先> --constants data/maimai_constants.json` |
| 2. 読み込み | CSV を読み、枠内 50 譜面（新曲 15 + ベスト 35）に絞る | `rating_detail.csv`（枠 = 新曲 / ベスト）+ `rating_summary.csv` |
| 3. 分析 | 4 節のロジック（ソート・差分・キャップ判定・シナリオ列挙） | 最新 CSV + `rating_core.py` の純関数（増分の再計算に使用） |
| 4. 提案 | 質問の種類に応じて回答を組み立て | なし（LLM 側の仕事） |

- 入力データの取得（NET → ブックマークレット等）は**ユーザー手動**。スキルは自動取得をしない。
- 出力先（CSV・分析メモ）は `data/` 配下など Git 対象外に置く（『プライバシー』）。

## 3. 入力パターンと分岐

### 3.1 入力パターン A: 既存スコア全体の分析

2 節のフローそのまま。最新の `rating_detail.csv` / `rating_summary.csv` をもとに 4 節のロジックで分析・提案する。

### 3.2 入力パターン B: ユーザー指定曲リストを加味した分析

ユーザーが「直近プレイで狙えそうなやつ」として、**曲名 + 達成率 + 新曲枠/ベスト枠の別（新/旧）** を
箇条書きで渡すケース。スキルはリスト 1 曲ごとに以下を順に処理する。

1. **定数の特定**: 定数 DB（`data/maimai_constants.json`）を曲名で引き、**候補を全列挙**する
   - タイトル重複（例: `Link` 2 件）と同一曲の ST/DX 同居は区別できないため、全候補を出す
   - 系統（ST/DX）・表示Lv・譜面難易度など、絞り込める情報があれば候補を絞る（なければ両方・全部で評価）
2. **現在レートの計算**: `rating_core.single_rate(定数, 達成率, is_ap)` を呼んで現在の単曲レートを算出
   （手計算でも算出できるが、切捨て・寸止め係数の処理を既存コードに寄せるのが確実）
3. **枠内との関係の判定**: 最新 CSV の枠内 50 譜面と突き合わせ
   - **既に枠内**なら「増分 = キャップ到達時レート − 現在レート」（押し出しは発生しない）
   - **圏外**なら「枠内最小との差」を評価。押し出し想定は **新曲枠最小 / ベスト枠最小** で、
     ユーザーの新/旧指定に応じて比較相手を切り替える
4. **キャップ到達時のレート**: floor(定数 × 1.005 × 22.4) + AP（domain.md『達成率』『Rank係数』。
   `capped_achievement()` で天井処理を既存コードに寄せる）
5. **枠に入った場合の押し出し増分**: (新しい譜面のレート − 押し出される枠内最小譜面のレート)。
   新/旧の別で押し出し相手が変わる点に注意（新曲枠の候補が上位 15 に入れない場合は圏外行きという
   枠構造も考慮。PoC の仮定に合わせる）
6. **狙い目評価**: 押し出し増分の大きい順に並べ、必要達成率とセットで提示する

- **達成率の記載がない曲（未達成・理論値のみ）も扱える**: 定数が特定できれば
  「達成率 X% で入れた場合のレート」を式で計算できる。代表的な達成率（ランク境界・100.5% 天井）での
  複数シミュレーションを並べて「最大でいくら入るか」を評価する。
- **ユーザー記載値の精度**: リストの達成率は簡易入力（桁数が NET 表示より粗い可能性）とみなし、
  結果は概算として提示する。正確な検証が必要なら NET から再取得（パターン A のフロー）に誘導する。
- **新/旧の裏取り**: ユーザーの新/旧指定を優先しつつ、追加バージョン（定数 DB・マスタ・
  `is_new_candidate()`）で整合チェックできる。DX 譜面の後からの追加等の境界ケースは要確認扱いにする。
- **成果物の置き場所**: この分析の成果物（リストの処理メモ・結果表など）をファイルに残す場合は
  `data/` 配下（Git 対象外）に置く。**実スコア数値を Git 管理対象のファイルに書かない**（会話内の
  表示は可否含め運用確認・未確定。6 節）。

## 4. 分析ロジックの要点（パターン A 共通）

- **ソートと底の特定**: 枠内 50 譜面を単曲レート降順に並べ、枠ごとの「底」（最下位）を特定する。
  水張り（枠内の下位譜面を鍛えたり高レート譜面で置き換えたりして底を引き上げること）の起点になる。
- **目標色との差分**: domain.md『RATING と色』の公式色表から目標色の下限を取得し、
  「残り = 下限 − 現 RATING」。通称（虹レ等）と下限の対応は質問時に確認する（例: 虹 ☆ = 15000）。
- **キャップ判定（これ以上伸びない譜面）**: 達成率は **100.5% で打ち止め**（domain.md『達成率』）。
  単曲レートの理論上限 = floor(定数 × 1.005 × 22.4) + AP（AP 未取得なら +1 の余地）。
  現在の達成率が既に天井に到達している譜面は「これ以上伸びない」として達成率面の分析対象から除外する。
- **定数の感覚値**: 同じ達成率・ランクなら **定数 0.1 の差は単曲レート約 2 ポイント**
  （0.1 × 1.005 × 22.4 ≒ 2.25。達成率・係数が下がると増分も縮む）。
  一方、ランク境界を 1 つ跨ぐと係数が 0.3〜0.8 跳ねるため、「定数の高い曲を探す」と
  「達成率の境界を越える」のどちらが効くかの比較軸になる。
- **水張り式の底上げシナリオ列挙**:
  1. 底上げ（既存譜面を鍛える）: 底側譜面を次のランク境界まで上げた場合の RATING 増分
  2. 置換（圏外候補と入れ替える）: `枠=圏外` の行（detail CSV に含まれる）が枠内の底の単曲レートを
     超えるための必要達成率を逆算（単曲レート式から概算。切捨て・境界に注意）
  3. AP 狙い: AP 未取得の枠内譜面は +1（プレイ難度は数値に含めず列挙のみ）
  - 各シナリオは RATING 増分の降順に並べる。実行難度（プレイ回数・習熟度）の判断はユーザーに委ねる。
- **制約の扱い**: `枠=未解決(定数なし)`・衝突未解決の行は分析対象外とする。

## 5. 出力のイメージ（ダミー数値）

```
現在地: RATING 15,123（虹 ☆）→ 目標「虹 ☆☆」まで 残り 127
候補 1: ダミー曲名 A2 を SS+（99.5%）まで → +X
候補 2: 圏外のダミー曲名 C1 を 98.0% 出せば ベスト枠最下位を置換 → +Y
（数値はすべてダミー・根拠とした行/CSV を添える）
```

## 6. 未確定・要検討リスト

- **配置場所**: このプロジェクト配下（例: `docs/` 隣接・専用 skills ディレクトリ）にするか、
  ユーザー横断の場所にするか。本実装（技術スタック未決定・ADR-0002）で参照先が変わる点に注意。
- **形態の分担**: (a) スキル = 手順書のみで LLM が CSV を読んで分析（柔軟・再現性は人依存）/
  (b) `analyze.py` 等のツールスクリプトを作り定番計算を任せる（再現性・テスト容易）/
  (c) ハイブリッド（定番計算はスクリプト、提案はスキル）。`rating_core.py` の純関数を再利用できるか。
- **実データ参照とプライバシー**: `data/` の読み込みはローカル実行なので問題ないはずだが、
  スキル本文に「実スコア数値を Git 管理対象のファイル・コミットに書かない」「成果物は `data/` 配下に置く」
  旨を明記する運用を確認。会話内への実値表示の可否も含めてユーザー確認。
- **入力形式の標準化**: 指定曲リスト（曲名 + 達成率 + 新/旧）を自由テキストのまま受け付けるか、
  項目の最小セットを決めるか。達成率なし・系統不明の扱いを含む。
- **再計算トリガ**: 毎回 `run.py` を再実行するか、CSV の鮮度確認のみか。入力 JSON の更新はユーザー手動。
- **目標指定の解釈**: 「虹レ」「白金」等の通称と下限値の対応表をスキルに持たせるか、質問時に都度確認するか。
- **出力形式**: 会話テキスト / Markdown 表 / CSV 添付のどれ。数値の根拠（参照した行）を必ず添えるか。
- **テスト**: スキル開発・動作確認はダミー入力（`poc/example_paste.txt` / `poc/example_bookmarklet.json`）で行い、
  実データは使用しない。
- **バージョン更新運用**: `run.py` の `--current-version` 既定（CiRCLE PLUS）の更新忘れを防ぐ注意書き。
