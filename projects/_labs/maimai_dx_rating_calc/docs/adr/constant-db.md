# 定数 DB は JSON で始め、ビューア実装時に RDB へ移行する

- Status: accepted
- Date: 2026-11-23

## 背景

RATING 計算には譜面定数が必要だが、公式マスタには含まれていない。DX 譜面の定数は別途収集が必要で、
数千行規模・実行時は読み取り専用。更新は「収集 → 検証 → 更新」の手順で行う。

定数は第三者サイト等を参照した手作業の収集で、出典サイト名を記載しない規則と、実データをリポジトリに
置かない方針がある（[conventions.md](../conventions.md)『出典』『プライバシー』）。そのため収集結果は
git 管理できず、更新履歴を git diff でレビューする手段も持てない。

将来のビューア実装では、曲の検索・絞り込み・画像キャッシュ管理が出てくる見込みで、実行時の読み取り全量では
足りなくなる。

## 決定

- 最初は JSON ファイルを正とする。実行時は `data/maimai_constants.json` を全量読み込む。
- この JSON は git 管理しない（`.gitignore` の `data/`）。出典をリポジトリの履歴に残さない規則と、
  実データをリポジトリに置かない方針に従う。
- 更新履歴のレビュー手段は git diff 以外で用意する。取り込みツールの整備と合わせて決め、この版では未定とする。
- ビューア実装時に SQLite / PostgreSQL へ移行し、JSON をシードとして投入する。移行先はビューアの
  技術スタックを決めるときに選ぶ。

## 採用しない案

- 最初から RDB を持つ: 実装初期に依存とスキーマ設計が要り、収集データの検証がしにくい。
- JSON を git 管理する: 出典を履歴に残さない規則に反し、実データをリポジトリに置かない方針とも合わない。
- 定数をコードや docs に埋める: 数千行・更新ありのデータを持ち運ぶ先として適さない。
- ビューアまで JSON のままにする: 検索・絞り込み・画像キャッシュを扱うには RDB が要る。
- 移行先を今決める: ビューアの要件（ホスティング・検索・画像）が未定で、決めても根拠が無い。

## 影響

- 実データは `data/` に置く。clone しただけでは RATING 計算はできず、定数データを別途用意する必要がある
  （PoC の `poc/constants.json` は 12 譜面のサンプル）。
- 更新履歴は git に残らない。必要になったら取り込みツール側で記録する。
- ビューア実装時に schema と移行手順を決める。それまでは JSON の形が実質のスキーマになる。
