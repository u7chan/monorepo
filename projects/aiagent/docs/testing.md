# テスト方針

## 実行

- `bun test` で全テストを実行する
- CI(Pull Request Check)は Docker の `test` ステージをビルドし、その中で `bun run lint` + `bun test` が通ることを検証する

## テストは生きるドキュメント

テストケースは仕様書として読めるように設計する。

- 期待値はリテラルで書き、テストコードを読むだけで仕様が分かる状態を保つ

## 構造化とスタイル

- テストケースは必ず `describe` でグループ化する。トップレベルに `test` / `it` を並べるフラットな書き方はしない
- ケースの宣言は `test` ではなく `it` に統一する。`describe("GET /healthz")` + `it("returns 200 ...")` が文章として読めるため（bun:test では両者はエイリアス）
- `describe` はエンドポイント・機能単位、`it` には期待する振る舞いをそのまま記述する

## テストは createApp() 経由で書く

- テストからは `src/app.ts` の `createApp()` を呼び出してアプリインスタンスを作る
- `src/index.ts`(エントリーポイント)を直接 import しない
- 理由: エントリーポイントは将来的に環境変数の読み込みやリスナー起動など副作用を持つようになる。`createApp()` 経由ならテストごとに独立したアプリを作れ、副作用に引きずられない
