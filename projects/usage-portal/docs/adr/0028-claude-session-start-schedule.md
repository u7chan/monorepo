# ADR 0028: Claude の 5 時間窓を、予約した時刻から 5 時間おきに開始する

- Status: accepted
- Date: 2026-11-21
- 一部置き換え: [ADR 0022](0022-claude-usage-via-cli.md) の「Claude へプロンプトは送らない。5 時間窓の開始も接続確認もしない」
- 関連: [ADR 0017](0017-probe-prompts.md) の最小プロンプト、[ADR 0026](0026-claude-card-visibility-and-logout.md) のログアウト

## 背景

Claude の 5 時間窓は、前の窓が終わったあとの最初の送信で始まる。使い始めの時刻しだいでリセットがコアタイムの
途中に来るかどうかが決まるので、窓の開始時刻を自分で揃えたい。たとえば 7:00 に開始しておけば 12:00 にリセットされ、
午前と午後で別の窓を使える。

ADR 0022 は、規約上の扱いが不透明な機械的な呼び出しを避けるため、Claude へのプロンプト送信をしないと決めた。
この ADR はその判断を、上限付きの予約送信に限って緩める。

## スパイク（2026-11-20、公式 CLI 2.1.328）

窓が動いている状態で、ホストの CLI から実行した結果。

- 次の送信は exit 0、`is_error: false`、`stop_reason: end_turn`、`result` は 1 文字だった。
  所要時間は CLI 全体で約 2.5 秒、API 部分で約 0.7 秒。
  ```
  claude -p "Reply with a single period." --model haiku --effort low \
    --system-prompt "Reply with exactly one character." --tools "" --strict-mcp-config \
    --setting-sources "" --disable-slash-commands --no-session-persistence --output-format json
  ```
- 消費量は入力が約 670 トークン（ほぼキャッシュ作成）、出力が 3 トークン、思考が 0 トークン。
  `--system-prompt` と `--tools ""` で、既定のシステムプロンプトとツール定義を外せている。
  送信の前後で `/usage` の値（5 時間・週次）は変わらなかった（整数への切り捨ての範囲に収まる）。
- `--model haiku --effort low` の組み合わせはエラーにならなかった。
- 存在しないモデルを指定すると exit 1、`is_error: true`、`api_error_status: 404` になった。
  失敗の分類は `api_error_status` から決められる。
- `/usage` のリセット時刻は `7:20pm` のように分を持っていた。窓の開始が時の頭へ丸められる、という仮説はこれで否定できる。
- CLI の `/usage` の整形コードによると、行の形は `<title>: <floor(utilization)>% used` で、`resets_at` があるときだけ
  ` · resets <日時>` が付き、`utilization` が `null` の窓は行ごと出ない。したがって窓が動いていないときは、
  `Current session` の行が無いか、行に `resets` が無いかのどちらかになる。既存の parser は `resetsAt: null` を許すので、
  「rolling 窓の `resetsAt` が無いか過去」を「窓が動いていない」と読める。

Haiku に短い文を送ると 5 時間窓が始まることは、利用者が Claude Desktop で確かめている（2026-11-20）。

確認できていないこと（窓が止まった状態を作れなかったため）:

- 窓の開始が送信時刻と何秒ずれるか（表示が分単位なので、最大 1 分ほどの誤差は見えない）
- CLI からの送信でも、Desktop と同じく窓が始まるか

これらは、実行のたびに送信後の `/usage` で実際のリセット時刻を記録し、履歴で予定と比べて確かめる。

## 決定

予約の形:

- 入力は「必ずリセットさせる時刻」（例: 22:00）、「1 日の回数」（1〜4）、「空ける時間」、曜日。
- 24 時間は 5 で割り切れず、連鎖を日をまたいで続けると開始が毎日 1 時間ずつずれる。窓は短くできないので、
  余りの「24 − 5 × 回数」時間は、窓を開始しない「空き」として 1 日に 1 か所に置く。空きのあとの最初の開始から、
  5 時間おきに回数ぶん開始する。翌日は同じ時刻からまた始めるので、毎日同じ時刻で回る。
- 空ける時間の候補は、必ずリセットさせる時刻を何番目の窓の終わりにするかで決まり、回数と同じ数だけある。
  22:00・4 回なら、空きは 3:00〜7:00（開始 7 / 12 / 17 / 22 時）、8:00〜12:00、13:00〜17:00、22:00〜2:00 の 4 つ。
  既定は、空きが 0:00〜7:00 と最も長く重なる候補（「おすすめ」）にし、利用者は一覧から選び直せる。
- 空きの間に Claude を使うと、そこで 5 時間の窓が始まり、次の枠の開始が見送りになることがある。
  そのため「必ず」は、空きの間に使わない限りでの保証になる。画面の空きの説明にもそう書く。
- 時刻は保存時のブラウザの IANA タイムゾーン付きで持つ。CLI は `TZ=UTC` のまま動かす。
- モデルと思考レベルはコードに既定値を置かず、選んで保存するまで予約を有効にできない（ADR 0017 と同じ方針）。
  モデルは CLI の別名（`haiku` / `sonnet` / `opus`）、思考レベルは `low` / `medium` / `high` から選ぶ。

1 枠の実行:

1. 送信前に `/usage` を読む（既存の `fetchClaudeUsage` で、auth status の判定も含む）。
   - rolling 窓が動いていない場合は送信する。
   - 窓が動いていて、リセットが枠の時刻から 30 分以内なら、リセットの直後まで待って 1 からやり直す。
     連鎖する 2 回目以降の枠は、前の窓が終わるちょうどその時刻に来るので、通常はこの経路を通る。
     待つ先は `/usage` の分単位の表示ではなく、前の窓をこのアプリが開始したときに記録した送信時刻の 5 時間 15 秒後にする。
     前の窓を自分で開始していない場合だけ、`/usage` のリセット時刻の 2 分後まで待つ。
   - 窓が動いていて、リセットがそれより後なら送らず「見送り（窓が動いていた）」と記録する。
   - 週次が 100% なら送らず「見送り（週次の上限）」と記録する。5 時間の窓を使い切っている場合は窓が動いているので、
     上の 2 つのどちらかで扱われ、上限のまま送ることはない。
2. 上の 1 行プロンプトを送る。上限は 60 秒（推論を伴うため、`/usage` の 15 秒とは分ける）。
   成否は exit code と JSON の `is_error` で判定し、`result` の本文は保存もログ出力もしない。
3. 送信に成功したら `/usage` を読み直し、snapshot を保存する。リセット時刻は履歴にも残す。
4. サーバーが止まっていて枠の時刻を過ぎた場合は、30 分以内なら遅れて実行し、それより遅ければ「見送り（時刻を過ぎた）」と記録する。

失敗と停止:

- 失敗は固定のコードへ丸める。送信前の確認で出たエラーは既存の `ProviderErrorCode` をそのまま使う。
  送信の失敗は `api_error_status` で分け、401 / 403 が `reauth_required`、429 が `limit_reached`、
  400 / 404 が `model_unavailable`、期限超過が `timeout`、それ以外が `unavailable`。
- 429（`limit_reached`）は失敗ではなく「見送り（上限）」として記録し、連続失敗に数えない。送信前の確認と送信のあいだに
  上限へ達する（`/usage` は割合を切り捨てて出すので、99% と出ていても実際は上限に近い）ことがあるため。
  上限は待てば戻り、次の枠で送り直せばよい。5 時間・週次・利用額のどの上限かは区別しない。
  CLI 内部の生成コードでは、上限は HTTP 429 で返り、`-p` の JSON に `api_error_status` として載る。
  実際に上限へ達した状態での出力は確認していないので、実装では fixture で固定し、運用中の履歴で確かめる。
- 予約の実行が 3 回続けて失敗したら、「自動で開始する」をオフにして理由を残し、それ以上送らない
  （連鎖の間隔では約 15 時間ぶん）。見送りは失敗に数えず、成功すると連続失敗の数を 0 に戻す。
  再開はスイッチをオンに戻す操作で行い、そのとき連続失敗の数を 0 に戻す。停止専用の状態や「再開」ボタンは持たない。
- ログアウト（ADR 0026）したら予約を無効にする。ログアウトはカードを消す操作なので、裏で送信を続けない。

画面:

- Claude カードの `⋮` に「開始予約」と「今すぐ開始」を足す。「今すぐ開始」は 1 の確認つきで 1 回だけ送り、
  履歴には残すが、連続失敗の数には影響しない。
- 予約が有効なとき、カードのフッターに 1 行だけ出す。
  - 通常時: 「次の開始 17:00 → 22:00 リセット」
  - 直前の実行が失敗したとき: 「開始に失敗（再ログインが必要）1/3」
  - 停止したとき: 「開始予約を停止中（3 回続けて失敗）」
  状態は色だけでなく文字でも示す。
- 「開始予約」のモーダルは「予約」と「履歴」の 2 タブにする。タブは既存の segmented control で作る。
  - 予約タブ: 「自動で開始する」のスイッチ、停止や失敗の知らせ、必ずリセットさせる時刻と回数、空ける時間（select）、
    24 時間のタイムラインと開始・リセットの 2 行、曜日、送信の設定（モデルと思考レベル）、保存。
    送信の設定はほとんど変えないので、折りたたんで「haiku / low」と要約だけを出す。未設定のときだけ開いて表示する。
  - 履歴タブ: 一覧と、見送りは失敗に数えないことの注記。直前の実行が失敗しているか停止中のときは、タブ名に印を付ける。
  - 失敗の知らせには「履歴を見る」を置き、履歴タブへ切り替える。
- スイッチは押した時点で保存する。保存ボタンは、時刻・回数・曜日・モデル・思考レベルの変更だけに使う。
  オン / オフは時刻の変更より頻繁に使うので、保存ボタンを押させない。モデルと思考レベルが保存されるまで、スイッチは押せない。
- 履歴は最小限の一覧で、直近 20 件の「予定時刻・結果（成功 / 見送り / 失敗 / 停止と、その理由）・実際のリセット時刻」を出す。
- 設定（時刻・回数・空き・曜日・タイムゾーン・モデル・思考レベル）と状態（オン / オフ・連続失敗の数・停止の理由・
  最後に送った時刻）は SQLite の `claude_start` に 1 行で置く。`DATA_DIR/settings.json` は Codex の送信設定の書き込みで
  ファイル全体を上書きするうえ、連続失敗の数のように実行のたびに変わる値を持たせるには向かないため。
- 履歴は SQLite の `claude_start_run` に置き、sample と同じ 30 日で消す。schema は v3 に上げる。
- 同じ枠を 2 回送らないよう、予約の枠の時刻を履歴に残し、処理済みの枠は飛ばす。サーバーを止めていた間の枠は、
  再起動後に 30 分以内なら送り、それより遅ければ、止まっていた長さにかかわらず最後に過ぎた枠だけを
  「見送り（時刻を過ぎた）」として 1 行残す（曜日を 1 つだけ選んだときの間隔に合わせ、8 日までさかのぼる）。
- 予約をオンにした・設定を保存した時刻を `claude_start` に残し、それより前の枠は、再起動をまたいでも遅れて送ることも
  見送りとして残すこともしない。メモリだけに持つと、オンにした直後の再起動で、オンにする前の枠を送ってしまう。

送信の内容:

- プロンプトとシステムプロンプトは毎回同じ固定文にする。時刻などの可変値は足さない。

## 理由

- 予約の起点を「リセット時刻」で受け取るのは、利用者が考えるのが「何時に窓が切り替わってほしいか」だから。
  開始時刻と空きの位置はアプリが逆算し、深夜に寄せた候補を既定にする。
- 送信前に `/usage` を読めば、窓が動いている間の無駄な送信を避けられる。送信後に読めば、Codex（ADR 0017）
  ではできなかった「予定どおり始まったか」の確認ができる。
- 同じ文面を送り続けても、技術的な問題は起きない。文面を変えて自動送信らしさを薄めるのは、「改変していない公式 CLI を、
  自分のアカウントで普通に使う」という ADR 0022 の前提と食い違う。可変値を足しても、ヘッドレスで Haiku に
  1 文字を返させる呼び出しであることは変わらない。
- 3 回で止めるのは、ログイン切れやモデル名の変化のように、時間が経っても直らない失敗で送信を繰り返さないため。

## 採用しない案

- 日をまたいで 5 時間おきに連鎖し続ける: 開始が毎日 1 時間ずつずれ、コアタイムに合わせる目的に合わない。
- 1 日 5 回にして 1 つを 4 時間の短い枠にする: 窓は短くできない。4 時間後に送っても前の窓がまだ動いているので見送りになり、
  連鎖が切れる。4 時間は窓の無い空きとして扱う。
- 枠の時刻に固定の余裕（たとえば 2 分）を足して送るだけにする: 前の窓の終わりと秒単位で競合し、窓が動いている間に送ると
  消費するだけになる。送信前に `/usage` を読んで待つ方が確実。
- 失敗したら 5 時間後まで待たずに短い間隔で再試行する: 通った時点で窓の開始がずれるうえ、時間で直らない失敗には効かない。
- 実行履歴を別のメニュー項目にする: `⋮` の項目が 5 つになり、失敗の知らせから履歴へ 1 タップで移れない。
  同じモーダルのタブにすれば、入口は 1 つのまま、縦の長さは 1 タブぶんで収まる。
- 履歴を予約の下に並べる: 一覧を足すとスマホで 2 画面を超える。
- 停止を有効 / 無効と別の状態にして「再開」ボタンを置く: 状態が 3 つになり、オフと停止の違いを説明する必要が出る。
  停止は「自動でオフになり、理由が残る」と表せば足りる。
- 連鎖の待ちを `/usage` のリセット時刻だけで決める: 表示は分単位で切り捨てて出るため、2 分ほどの余裕を足すことになり、
  連鎖するたびに開始が遅れて「必ずリセットさせる時刻」が 1 日で数分ずれる。自分で送った時刻を基準にすれば、
  ずれは 1 回 15 秒ほどに収まり、翌日は空きのあとの起点からやり直すので持ち越さない。
- 時刻を付けて毎回プロンプトを変える: 理由に書いたとおり。

## 影響

- Claude へのプロンプト送信は、予約が有効な日に限り最大 1 日 4 回になる。CLI の起動は 1 枠につき最大 5 回
  （送信前の auth status と `/usage`、送信、送信後の auth status と `/usage`）。
- 予約の送信と画面からの更新・ログアウトは、同じ CLI の資格情報を使う。実行は Claude の single-flight にそろえて直列にする。
- 規約の解釈は変わり得る。共有、複数アカウント、送信回数の上限の引き上げは、この ADR を見直してから行う。
- 未確認の 2 点（Haiku の送信で窓が始まるか、開始のずれ）は、最初の数回の履歴で確かめ、結果をこの ADR に追記する。
