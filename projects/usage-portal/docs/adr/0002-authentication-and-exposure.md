# ADR 0002: 入口の認証と公開範囲（6 桁 PIN、自宅 LAN / VPN 前提）

- Status: accepted
- Date: 2026-10-25

## 背景

画面は読み取り専用だが、どの利用枠がどれだけ残っているかは外に見せたくない。利用端末は自宅 LAN のスマホと PC で、出先では VPN 経由で
自宅 LAN に入る。ユーザーは 1 人しかおらず、ユーザー管理、パスワード変更、複数端末の使い分けは要らない。

利用枠を守るのは上流の認証情報であり、入口の認証ではない。入口に求めるのは「誰でも開ける状態を避ける」ことで、
通信の秘匿や、LAN 内の盗聴への対策ではない。

候補は、認証なし、Basic 認証、6 桁 PIN と署名付き cookie、パスキー / TOTP、インターネット公開と TLS の組み合わせ。

## 決定

- 6 桁の数字 PIN を 1 つだけ持つ。PIN は Argon2id のハッシュだけを保持し、環境変数 `PIN_HASH_B64`（base64url）で渡す。
- ログイン成功で署名付き HttpOnly cookie を発行する。サーバー側のセッションは持たず、有効期間は 30 日。残り 3 日で再ログインを促す。
- ログイン試行はメモリ上の sliding window で制限する。5 回失敗したら 15 分ロックし、`Retry-After` を返す。
- 公開範囲は自宅 LAN または VPN の内側だけ。`0.0.0.0:3001` で待ち受け、インターネットへは公開しない。TLS 終端は v1 のスコープ外とし、HTTP のまま使う。
- 認証 API と `/api/usage` は `Cache-Control: no-store` を付け、`POST` は同一 origin のときだけ受け付ける。

採用しない案:

- 認証なし: 読み取り専用でも、利用状況は同じネットワークの誰にでも見せない。
- Basic 認証: ブラウザのダイアログとアプリの画面が二重になり、cookie の期限やログアウトをアプリ側で扱えない。
- パスキー / TOTP: 1 ユーザーの入口には過剰。総当たり耐性は Argon2id とレート制限で補う。
- インターネット公開 + TLS 必須: 6 桁 PIN はインターネット公開に耐える強度ではない。公開するなら認証方式ごと変える。

## 理由

- PIN 1 つなら、ユーザー管理もパスワード再発行も持たずに済む。入力はスマホで 6 桁を打つだけ。
- 署名付き cookie にすれば、サーバー側のセッションテーブルを持たなくても期限を表現できる。
- 自宅 LAN と VPN の内側だけなら、HTTP のままで実用上足りる。TLS を足すのは、公開範囲を広げるときでよい。

## 影響

- cookie を盗まれた場合、有効期限まで使える。ログアウトはブラウザの cookie を消すだけで、サーバー側の失効リストは持たない。この用途では許容する。
- PIN を変えると `PIN_HASH_B64` が変わり、全端末がログアウトされる。署名鍵に PIN ハッシュを含めるため。
- LAN 内の盗聴までは防がない。HTTPS が要る構成（VPN の外に出す、前段に TLS 終端を置く）になったら `COOKIE_SECURE` と `TRUST_PROXY` を設定する。
- この PR（PR 分割の 1）で入るのは、`/api/health` が使う設定の検証だけ。`PIN_HASH_B64` を base64url で decode して `$argon2id$` で始まること、
  `SESSION_SECRET` が 32 bytes に decode できることを見て、崩れていれば `auth: misconfigured` と 503 を返す。
- ログイン、cookie、認証 middleware、レート制限、ログイン画面、期限バナーは 2 番目の PR で入る。
