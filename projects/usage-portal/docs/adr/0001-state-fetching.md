# ADR 0001: 状態の取得（BFF のポーリング、SSE は使わない）

- Status: accepted
- Date: 2026-10-25

## 背景

利用枠の変化は分単位で、画面から利用枠を変える操作は無い。表示するのは「今どれだけ残っているか」と「いつリセットされるか」だけで、
秒単位の即時性は要らない。上流 API は公開契約ではなく、失敗したときは前回の値を保持して stale と表示する必要がある。

候補は、BFF が上流をポーリングしてスナップショットを返す方式と、ブラウザへ変化を押し出す方式（SSE / WebSocket）、
client から上流を直接叩く方式。

## 決定

- BFF が 5 分ごとに上流をポーリングし、正規化したスナップショットを SQLite に保存する。取得は single-flight とし、前の取得が終わる前に次を始めない。
- Client は 60 秒ごとに `GET /api/usage` を叩き、BFF が保存したスナップショットを取得する。
- `GET /api/usage` は認証済みなら常に 200 を返し、provider の失敗は payload の `state`（`loading` / `ok` / `stale` / `error`）と `error.code` で表す。
- `Cache-Control: no-store` を付ける。

採用しない案:

- SSE / WebSocket: 変化が遅く、操作も無い。再接続、スナップショットの再適用、接続状態の表示を持ち込む理由が無い。
- client から上流を直接叩く: OAuth の token と API key をブラウザへ渡すことになる。認証情報は BFF とコンテナ内のファイルだけに置く。
- メモリだけに保持する: 再起動後に前回値と 24 時間の推移を出せない。

## 理由

- 1 本の GET のポーリングなら、状態は「取得できたスナップショット」と「最後に失敗した時刻」の 2 つだけで表せる。
- BFF が上流のポーリングを担うため、ブラウザを閉じている間も snapshot が更新され、開いた直後に前回値が出る。
- 保存を挟むことで、上流が落ちても前回値を stale として出せる。`pi-console` の usage と同じ振る舞いになる。

## 影響

- ポーリング間隔は `POLL_INTERVAL_MS`（既定 300000）で変えられる。client の間隔は 60 秒固定で、BFF の設定に追従しない。
- provider ごとに独立して失敗を扱う。片方が失敗しても、もう片方のスナップショットは更新する。
- この PR（PR 分割の 1）で入るのは `GET /api/health` だけ。sampler、`/api/usage`、provider adapter は 4 番目の PR、client のポーリングと表示は 5 番目の PR で入る。
- 即時性が要る画面（サインインの進行表示など）は、この方針の例外として 2 秒間隔の GET を使う。SSE は使わない。
