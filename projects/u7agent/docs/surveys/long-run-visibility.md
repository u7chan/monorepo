# 長時間ランの可視化と追加入力の扱い

実行中の会話に対して利用者が「いま何をしているか」を知ろうとしたときの現行の挙動と、今後採り得る案。**未着手**で、ここに書くのは決定ではなく検討の記録。現行の契約は [run-lifecycle.md](../run-lifecycle.md#追加入力steeringの配送) と [api-sessions.md](../api-sessions.md) を正とする。

## 現行の挙動（観測）

- 実行中に送った入力は steering として次のモデル判断の前へ注入される。**注入されたことと、モデルがその入力へ答えることは別**で、モデルが作業の続行を選べば本文を出さないままツール実行が続く。
- steering は実行中のツールを止めない。長いツールが走っている間の入力は、そのツールが終わるまで注入されない。
- 中断できるのは停止だけ。停止は実行中のツールも止めるため、「質問したいだけ」の用途には重い。
- 状態行の経過時間は run 全体の経過で、直前のツールの所要時間ではない。run は追加入力・再試行・圧縮では切れない。

## 候補

### 1. 中断して送信する（未着手）

実行中の入力を、待たずに現在の run を終わらせてから新しい run として始める導線。停止の経路と未配送入力の回収を使う。作業途中のファイルが残り得るため、操作時に確認を出す。

### 2. 進捗を即時表示する（採用しない）

現在のツール・経過・直近の完了を、モデルを介さずに表示する案。状態から答えられる質問には有効だが、専用 UI を増やす割に得られる情報が少ない。長時間タスクの計画（次項）で代替する。

### 3. 長時間タスクの TODO リスト（未着手）

モデルに最初の応答で手順を作らせ、常設の一覧に出す。成立の条件は次の 4 つ。

- 構造化した状態として保存し、リロードや再接続でも同じものを見せる
- 最終更新時刻を併記し、古いままなら「更新が止まっている」と分かるようにする
- 現在のツールと run の経過を並べる。TODO はモデルの自己申告で、意図しか表さない
- 状態と食い違ったら状態を優先する。更新されない TODO を進捗の保証として扱わない

### 4. ツールの実行上限（未着手）

1 回のツール実行に既定の上限時間を設け、超えたらタイムアウトとしてモデルへ返して次の判断へ進ませる。常駐プロセスを起動するツールは対象外。既定値を短くしすぎると正当な処理を切るため、値は運用で決める。

## 非ゴール

- プロンプトで「割り込みには必ず答える」を強制すること。モデルの追従は保証できない。
- 停止を「質問のための軽い操作」にすること。停止は作業を中断する。
- 実行中の入力を本文から自動判定して横取りすること。通常の指示を奪い得る。
