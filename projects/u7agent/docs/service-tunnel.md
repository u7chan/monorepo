# 一時共有（Cloudflare Quick Tunnel）の起動基盤

動いているサービスを Cloudflare Quick Tunnel で一時的に外へ公開するための、`cloudflared` の配布・解決・起動・停止の契約。**引数・env の許可リスト・期限の値の正は `server/src/cloudflared.ts`** で、テストは `server/test/cloudflared*.test.ts`（実プロセスと実ネットワークは使わない）。ここには、利用者から見た振る舞いが変わらない変更では書き換えが要らない文（契約・採らなかった案・既知の制限）だけを書く。サンドボックスとの境界は [sandbox.md](sandbox.md)、BFF が秘密を子へ渡さない層は [secrets.md](secrets.md#レイヤー) を参照する。

この文書が扱うのは起動基盤だけで、公開の制御（ゲート）・状態・API・GUI は、それを実装する変更が追記する。背景と全体の設計は [#2804](https://github.com/u7chan/monorepo/issues/2804)。

## 位置づけ

Quick Tunnel の実体は別バイナリの `cloudflared` で、BFF が起動・停止・監視する層が要る。この層は「`launch` したら、向き先のポートを公開するプロセスと、その URL が手に入る」ことだけを持つ。ゲートや状態を上の層が作るときは、この層を fake に差し替えて作れる。

## 契約

- **BFF が子プロセスを起こす唯一の例外**: BFF は子プロセスを起こさない（[AGENTS.md](../AGENTS.md#構成)）。例外は `cloudflared` の起動 1 本だけで、資格情報を使わないこと、別プロセスで BFF のメモリと env から切り離せること、引数と向き先が固定であることが理由。lint が `server/src/` の `child_process` の import を、`server/src/sandbox/` と `server/src/cloudflared.ts` だけに限る。ただし `createRequire` 経由の読み込みは検出しないので、lint は柵であって境界ではない
- **資格情報を渡さない**: 子の env は許可リストで、BFF の env は継承しない（LLM のキー・master key・サンドボックスとの共有トークンを子へ渡さない）。`HOME` と作業ディレクトリは起動ごとに作る専用のディレクトリで、stdin は閉じる
- **`PATH` を探さない**: 使うバイナリは `PI_CLOUDFLARED_PATH`、イメージの固定の置き場、dev の固定の置き場の順。`PI_CLOUDFLARED_PATH` を指定したときはそれだけを見て、使えなくても別の候補へ落とさない（意図しないバイナリを黙って使わない）。どの候補も実体を `realpath` で解決し、通常ファイルで実行できることを確かめる
- **エージェントが書ける場所のバイナリと置き場は使わない**: 実体が Landlock の固定の書き込み先（`/tmp`・ホーム配下のキャッシュなど）、ワークスペースの root、共通スキルの root（`<workspace>/.agents/skills`）のいずれかの配下なら、`PI_CLOUDFLARED_PATH` で指されても使わない。エージェントがバイナリを差し替えると、BFF がそれをサンドボックスの外で起動することになるため。symlink で外から入れても、実体で判定する
- **dev の置き場は、サンドボックスの `PATH` に足すラッパーの置き場と別にする**: 同じ場所に置くと、エージェントが `cloudflared` を名前で呼べる。ブラウザの配布の既定の置き場（`~/.cache` 配下）にも倣わない。そこは書き込み先で、置いたバイナリをエージェントが差し替えられる。配布スクリプトも BFF と同じ書き込み先の判定を使い、書き込み先なら既存のコピーの確認も、一時ファイルの実行も、公開もしない（既存の実体も、ハッシュの確認前と実行の直前に実体で判定する）。判定は取得の前後で root を取り直し、取得中に実体が変わっても古い一覧で実行しない。同じ配置先を使うインストールは、検証・削除・公開をロックで直列にする（片方の失敗が、もう片方の検証済みのコピーを消さないため）。ロックは mtime ではなく持ち主の pid と起動時刻で外し、ダウンロードと待ちには上限を置く
- **向き先は loopback のゲートだけ**: `--url` に渡すのは、呼び出し側が渡す loopback のポートだけ。外部の入力を引数へ連結しない
- **設定ファイルを読ませない**: 設定は `/dev/null`（空）を渡す。エージェントが書ける場所に設定ファイルを置かれると、その ingress が `--url` より優先され、向き先を差し替えられるため。起動のたびに出る「設定が空」の Error 行は、失敗として扱わない
- **メトリクスは loopback の一時ポート**: 公開 URL と準備の確認に使う。メトリクスのリスナーは `/config` と `/debug/pprof/` も出すので loopback に限り、ポートは OS の一時ポートにする。dev のサンドボックスから届かないのは、Landlock の接続先ポートの許可リストの外だからで、固定の範囲へ変えない。ポートは cmdline から誰でも読め、確保から子が待ち受けるまでに別のプロセスが先に取り得るので、待受が子自身のものと確かめられるまで、その応答を採らない。確認は、IPv4 の `127.0.0.1:<port>` の LISTEN の inode が子の fd にあり、繋ぎ先が子のものだと**確かめられたときだけ**採り、観測できないときは採らない。応答を採る直前にもう一度確かめる（先に取られたときは、子が待ち受けられず起動の失敗になる。再試行は呼び出し側）
- **URL は `/quicktunnel`、準備は `/ready`**: URL はメトリクスの `/quicktunnel` を正にする。取れないときだけ、起動ログの `https://<name>.trycloudflare.com` を代わりに使う（免責文のリンクや作成 API の URL は拾わない）。URL が出ていても、エッジへの接続ができて `/ready` が 200 になるまでは解決しない。**`/ready` が 200 でも、公開ホスト名が引けるとは限らない**ので、それを確かめるのは呼び出し側の責務
- **置き場は会話ストア配下**: 専用 `HOME` と、孤児の掃除のための記録を、会話ストアの `tunnel/` に置く。起動のたびに実体を解決し、エージェントが書けない場所の、専用のディレクトリ（ファイルや、外を指す symlink ではない）であることを確かめる。会話ストアが無い構成（永続化なし）では使えない。使えない理由は分類で返し、起動ログには利用可否の 1 行だけを出す（パスは出さない）
- **対象の OS**: Linux（`/proc` と pidfd を使う）。macOS と Windows は対象外（設定に渡す `/dev/null` が Unix の前提で、待受の所有確認と孤児の掃除を同じ強さでできない）
- **停止は呼び出し側がゲートを閉じてから**: 子へ SIGTERM を送り、猶予のあと SIGKILL。起動中でも止められ、冪等で、専用 `HOME` と記録も消す。止められなかった子の記録と専用 `HOME` は、次の掃除が見つけられるよう残す。BFF の終了処理が走らない経路（例外・`process.exit`）でも、生きている子を最後に殺す
- **孤児を掃除する**: BFF が SIGKILL されると、子と公開 URL が残り得る。出力のパイプが閉じるので子が先に終わることもあるが、それに頼らない。次の BFF の起動で、**書いた BFF がもう居ないときだけ**、記録ではなく実際のプロセスが、実体・起動時刻・cmdline・作業ディレクトリ・引数の形のすべてで記録と一致する子だけを止める。専用 `HOME` は記録のファイル名から導出し、記録の中の `home` は根拠にしない。書き換えられた記録で他のプロセスを殺せないよう、一致しなければ何も殺さない。記録を消すのは、その `HOME` のロックが外れているときだけ。signal は、照合したあとに開いた pidfd へ送る（数値の pid へは落とさない）。同じ会話ストアを使う別の BFF の稼働中の共有には触らない。`/proc` を読めないとき、pidfd を開けないとき、照合が観測不能のときは、何も殺さず記録と専用 `HOME` を残す
- **起動元の生存は、起動ごとの flock で確かめる**: 起動のたびに専用 `HOME` の中に `launch.lock` を作り、起動元が排他ロックを持つ。カーネルはプロセスの終了でロックを外すので、`ppid` と違って BFF 自身が PID 1 のときの自分の子と、孤児を引き取った subreaper を区別できる。掃除はロックを非ブロッキングで試し、取れなければ起動元が生きている（止めない）、取れれば孤児（照合のうえで止める）。ロックを取れない環境では起動しない。記録は `HOME` より先に書き、子を起こした直後に pid と固定の引数で更新し、`/proc` から起動時刻を読めたら確定する。起動時刻まで確定できない記録は送信の根拠にせず、記録と `HOME` を残す（自動では回収しない）。`spawn` を始めた記録も、子が居ない記録と区別して消さない。記録の削除や `HOME` の削除の前にもロックを見るので、壊れた記録があっても、生きている起動元の `HOME` は消さない
- **記録の一覧が読めないときは、何も消さない**: 個々の記録だけでなく、置き場の一覧の読み取りに失敗したときも、不在とみなして `HOME` を消さない（記録だけ残って `HOME` が消えるのを避ける）
- **起動の確認は 1 本の期限で、成功で上書きしない**: 期限は `launch` からの 1 本を単調時計の絶対時刻で持ち、掃除・観測・所有確認・probe と、`spawn` と成功の直前の同期確認に使う。停止・子の終了・期限のどれが起きても、確認の途中の応答で `ready` を成功にしない。`ready` の reject は書き込みや `mkdir` の完了を待たない（後片付けは順序を守る）。期限による停止は `ready` の確定までで、確定後の共有は明示的な `stop()` だけが止める
- **失敗は分類して返す**: 利用不可・ネットワーク・作成の拒否（429 を含む）・期限・予期しない終了。文言は呼び出し側が分類ごとに固定で持ち、`cloudflared` の生の出力は載せない。ログへ出す文字列は `*.trycloudflare.com` をマスクする（URL が共有そのものであるため）。作成の拒否は自動で再試行しない

## 版の更新

版と sha256（linux の amd64 / arm64）は配布スクリプト `scripts/install-cloudflared.mjs` の定数で、更新は手動（Dependabot の対象外）。`cloudflared` のサポートは直近 1 年の版に限られるので、定期的に上げる。

1. 新しい版のリリース asset の sha256 を、amd64 と arm64 の両方で取り直し、定数を更新する
2. 固定した版の `tunnel --help` で、起動の引数が通ることを確かめる（フラグの位置と、`--protocol` の有無は版で変わり得る）
3. 実機で 1 回起動して、`/quicktunnel` と `/ready` の応答の形と、起動ログの文言を確かめ、テストの fixture（`server/test/fixtures/cloudflared-output.ts`）を実物の出力から取り直す。ホスト名・IP・ID・拠点は架空の値へ置き換える
4. イメージは、ビルドで sha256 の照合と `--version` の実行が通ることを確かめる

## 採らなかった案

- **`PATH` の探索**: エージェントが書ける場所のバイナリを拾い、BFF がサンドボックスの外で起動することになる
- **BFF の env の継承**: LLM のキーと master key が子へ渡る。許可リストにする
- **`--pidfile` への依存**: 最初の接続のあとにしか書かれないので、起動中の中断や、起動の途中で BFF が落ちたときの子を扱えない。BFF 自身が書く記録を正にする
- **ログ解析だけの URL 取得**: ログの文言は版で変わる。`/quicktunnel` を正にし、ログに頼るのは URL の代替取得と失敗の分類だけにする
- **書き込める場所への設定ファイル**: ingress が `--url` より優先され、向き先を差し替えられる。空の設定を渡す
- **公式の Docker イメージからの COPY**: arm64 への対応と、distroless のバイナリが trixie で動くかが未確認で、版を dev の導入スクリプトと 2 か所で持つことになる。リリースの asset を sha256 で固定して取得する
- **異常終了した `cloudflared` の自動再起動**: `serve` と同じく、自動復旧は持たない

## 既知の制限

- 起動時刻を確定できなかった記録は、自動では回収しない。`spawn` の直後に BFF が落ちた場合などで、記録と `HOME` が残る。
- 配布のロックは、持ち主の pid と起動時刻で生存を見る。持ち主の判定から新しいロックを取るまでの間に、別の取得者が古いロックを外す競合が残る（同時実行は `pnpm dev` の二重起動程度で、失敗した側は再実行で回復する）。`.install.lock` が FIFO だと読み取りが返らず、待ちの上限も効かない。配置先にそれを置ける状況は、既にバイナリを差し替えられる状況なので想定しない。
- 起動元の確認は flock が前提。flock を持てないファイルシステム（一部の NFS など）や、`node:ffi` の無いビルドでは起動できない（`lock_unavailable`）。
- 孤児の掃除は best-effort で、Linux の `/proc` と pidfd が前提。記録を書く前に BFF が SIGKILL された場合と、実体のバイナリを差し替えたあとの古い子は、掃除できない。pidfd は Node の `node:ffi` で開く。FFI の無いビルド（`--no-experimental-ffi`、非公式ビルド）では起動元のロックも取れないため起動しない（数値の pid へは落とさない）。掃除に失敗したときは起動ログに `could not stop` として出る
- 作成は、短時間に多数だと 429 で拒否される。上限も回復時間も公開されていない。作成と停止の繰り返しを前提にしない
- 外向きに 7844 の TCP / UDP と、`api.trycloudflare.com` の 443 が要る。7844 に届かないときは、QUIC から HTTP/2 への切り替えが続き、ネットワークの失敗ではなく期限切れに見える可能性がある（未確認）。HTTP プロキシ経由の環境は想定しない（env を渡さないため）
- エージェントが書ける場所の判定は、Landlock の固定の書き込み先・ワークスペースの root・共通スキルの root に限り、起動のたび・配置のたびの時点のもの。判定のあとに書き込み先が差し替えられる場合は守れない。それ以外の場所をエージェントが書ける構成は想定しない
- 起動のロックは通常ファイルを前提にする（FIFO や symlink は開かない）。配置先にそれらを置ける状況は、既にバイナリを差し替えられる状況なので想定しない。NFS 上の flock は保証しない
- `PI_CLOUDFLARED_PATH` は、利用者が指す任意のバイナリを実行する。BFF の設定（env）を書ける人は、もともと BFF の実行内容を決められる前提とする
