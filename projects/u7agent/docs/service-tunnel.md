# 一時共有（Cloudflare Quick Tunnel）

動いているサービスを Cloudflare Quick Tunnel で一時的に外へ公開するための、`cloudflared` の配布・解決・起動・停止と、ゲート・状態・API の契約。**引数・env の許可リスト・期限の値の正は `server/src/cloudflared.ts`**、ゲートの応答と同一性の判定は `server/src/tunnel-gate.ts`、状態機械と期限は `server/src/service-tunnel.ts`、DTO は `server/src/schema/` を正とし、テストは `server/test/cloudflared*.test.ts`・`tunnel-gate.test.ts`・`service-tunnel.test.ts`・`tunnel-api.test.ts`（cloudflared の実プロセスと外部ネットワークは使わない）。画面の状態・文言・通知の規則は `client/src/lib/serveTunnel.ts` を正とし、テストは `client/test/serveTunnel.test.ts` と `client/test/serveTunnelEntry.test.ts`。ここには、利用者から見た振る舞いが変わらない変更では書き換えが要らない文（契約・採らなかった案・既知の制限）だけを書く。サンドボックスとの境界は [sandbox.md](sandbox.md)、BFF が秘密を子へ渡さない層は [secrets.md](secrets.md#レイヤー) を参照する。

背景と全体の設計は [#2804](https://github.com/u7chan/monorepo/issues/2804)。状態名・終了の理由・期限の値の一覧は書かない（正は `server/src/service-tunnel.ts` と `server/src/schema/`）。

## 位置づけ

Quick Tunnel の実体は別バイナリの `cloudflared` で、BFF が起動・停止・監視する層が要る。この層は「`launch` したら、向き先のポートを公開するプロセスと、その URL が手に入る」ことだけを持つ。ゲートや状態を上の層が作るときは、この層を fake に差し替えて作れる。

## 契約

- **BFF が子プロセスを起こす唯一の例外**: BFF は子プロセスを起こさない（[AGENTS.md](../AGENTS.md#構成)）。例外は `cloudflared` の起動 1 本だけで、資格情報を使わないこと、別プロセスで BFF のメモリと env から切り離せること、引数と向き先が固定であることが理由。lint が `server/src/` の `child_process` の import を、`server/src/sandbox/` と `server/src/cloudflared.ts` だけに限る。ただし `createRequire` 経由の読み込みは検出しないので、lint は柵であって境界ではない
- **資格情報を渡さない**: 子の env は許可リストで、BFF の env は継承しない（LLM のキー・master key・サンドボックスとの共有トークンを子へ渡さない）。`HOME` と作業ディレクトリは起動ごとに作る専用のディレクトリで、stdin は閉じる
- **`PATH` を探さない**: 使うバイナリは `PI_CLOUDFLARED_PATH`、イメージの固定の置き場、dev の固定の置き場の順。`PI_CLOUDFLARED_PATH` を指定したときはそれだけを見て、使えなくても別の候補へ落とさない（意図しないバイナリを黙って使わない）。どの候補も実体を `realpath` で解決し、通常ファイルで実行できることを確かめる
- **エージェントが書ける場所のバイナリと置き場は使わない**: 実体が Landlock の固定の書き込み先（`/tmp`・ホーム配下のキャッシュなど）、ワークスペースの root、共通スキルの root（`<workspace>/.agents/skills`）のいずれかの配下なら、`PI_CLOUDFLARED_PATH` で指されても使わない。エージェントがバイナリを差し替えると、BFF がそれをサンドボックスの外で起動することになるため。symlink で外から入れても、実体で判定する
- **dev の置き場は、サンドボックスの `PATH` に足すラッパーの置き場と別にする**: 同じ場所に置くと、エージェントが `cloudflared` を名前で呼べる。ブラウザの配布の既定の置き場（`~/.cache` 配下）にも倣わない。そこは書き込み先で、置いたバイナリをエージェントが差し替えられる。配布スクリプトも BFF と同じ書き込み先の判定を使い、書き込み先なら既存のコピーの確認も、一時ファイルの実行も、公開もしない（既存の実体も、ハッシュの確認前と実行の直前に実体で判定する）。判定は取得の前後で root を取り直し、取得中に実体が変わっても古い一覧で実行しない。同じ配置先を使うインストールは、検証・削除・公開をロックで直列にする（片方の失敗が、もう片方の検証済みのコピーを消さないため）。ロックは mtime ではなく持ち主の pid と起動時刻で外し、ダウンロードと待ちには上限を置く
- **向き先は loopback のゲートだけ**: `--url` に渡すのは、呼び出し側が渡す loopback のポートだけ。外部の入力を引数へ連結しない
- **設定ファイルを読ませない**: 設定は `/dev/null`（空）を渡す。エージェントが書ける場所に設定ファイルを置かれると、その ingress が `--url` より優先され、向き先を差し替えられるため。起動のたびに出る「設定が空」の Error 行は、失敗として扱わない
- **メトリクスは loopback の一時ポート**: 公開 URL と準備の確認に使う。メトリクスのリスナーは `/config` と `/debug/pprof/` も出すので loopback に限り、ポートは OS の一時ポートにする。dev のサンドボックスから届かないのは、Landlock の接続先ポートの許可リストの外だからで、固定の範囲へ変えない。ポートは cmdline から誰でも読め、確保から子が待ち受けるまでに別のプロセスが先に取り得るので、待受が子自身のものと確かめられるまで、その応答を採らない。確認は、IPv4 の `127.0.0.1:<port>` の LISTEN の inode が子の fd にあり、繋ぎ先が子のものだと**確かめられたときだけ**採り、観測できないときは採らない。応答を採る直前にもう一度確かめる（先に取られたときは、子が待ち受けられず起動の失敗になる。再試行は呼び出し側）
- **URL は `/quicktunnel`、準備は `/ready`**: URL はメトリクスの `/quicktunnel` を正にする。取れないときだけ、起動ログの `https://<name>.trycloudflare.com` を代わりに使う（免責文のリンクや作成 API の URL は拾わない）。URL が出ていても、エッジへの接続ができて `/ready` が 200 になるまでは解決しない。**`/ready` が 200 でも、公開ホスト名が引けるとは限らない**ので、それを確かめるのは呼び出し側の責務
- **置き場は会話ストア配下**: 専用 `HOME` と、孤児の掃除のための記録を、会話ストアの `tunnel/` に置く。起動のたびに実体を解決し、エージェントが書けない場所の、専用のディレクトリ（ファイルや、外を指す symlink ではない）であることを確かめる。会話ストアが無い構成（永続化なし）では使えない。使えない理由は分類で返し、起動ログには利用可否の 1 行だけを出す（パスは出さない）
- **対象の OS**: Linux（`/proc` と pidfd を使う）。macOS と Windows は対象外（設定に渡す `/dev/null` が Unix の前提で、待受の所有確認と孤児の掃除を同じ強さでできない）
- **停止は呼び出し側がゲートを閉じてから**: 子へ SIGTERM を送り、猶予のあと SIGKILL。起動中でも止められ、冪等で、専用 `HOME` と記録も消す。止められなかった子の記録と専用 `HOME` は、次の掃除が見つけられるよう残す。BFF の終了処理が走らない経路（例外・`process.exit`）でも、生きている子を最後に殺す
- **孤児を掃除する**: BFF が SIGKILL されると、子と公開 URL が残り得る。出力のパイプが閉じるので子が先に終わることもあるが、それに頼らない。次の BFF の起動で、**書いた BFF がもう居ないときだけ**、記録ではなく実際のプロセスが、実体・起動時刻・cmdline・作業ディレクトリ・引数の形のすべてで記録と一致する子だけを止める。専用 `HOME` は記録のファイル名から導出し、記録の中の `home` は根拠にしない。書き換えられた記録で他のプロセスを殺せないよう、一致しなければ何も殺さない。記録を消すのは、その `HOME` のロックが外れているときだけ。signal は、照合したあとに開いた pidfd へ送る（数値の pid へは落とさない）。同じ会話ストアを使う別の BFF の稼働中の共有には触らない。`/proc` を読めないとき、pidfd を開けないとき、照合が観測不能のときは、何も殺さず記録と専用 `HOME` を残す
- **起動元の生存は、起動ごとの flock で確かめる**: 起動のたびに専用 `HOME` の中に `launch.lock` を作り、起動元が排他ロックを持つ。カーネルはプロセスの終了でロックを外すので、`ppid` と違って BFF 自身が PID 1 のときの自分の子と、孤児を引き取った subreaper を区別できる。掃除はロックを非ブロッキングで試し、取れなければ起動元が生きている（止めない）、取れれば孤児（照合のうえで止める）。ロックを取れない環境では起動しない。記録は `HOME` より先に書き、子を起こした直後に pid と固定の引数で更新し、`/proc` から起動時刻を読めたら確定する。起動時刻まで確定できない記録は送信の根拠にせず、記録と `HOME` を残す（自動では回収しない）。`spawn` を始めた記録も、子が居ない記録と区別して消さない。記録の削除や `HOME` の削除の前にもロックを見るので、壊れた記録があっても、生きている起動元の `HOME` は消さない
- **記録の一覧が読めないときは、何も消さない**: 個々の記録だけでなく、置き場の一覧の読み取りに失敗したときも、不在とみなして `HOME` を消さない（記録だけ残って `HOME` が消えるのを避ける）
- **起動の確認は 1 本の期限で、成功で上書きしない**: 期限は `launch` からの 1 本を単調時計の絶対時刻で持ち、掃除・観測・所有確認・probe と、`spawn` と成功の直前の同期確認に使う。停止・子の終了・期限のどれが起きても、確認の途中の応答で `ready` を成功にしない。`ready` の reject は書き込みや `mkdir` の完了を待たない（後片付けは順序を守る）。期限による停止は `ready` の確定までで、確定後の共有は明示的な `stop()` だけが止める
- **失敗は分類して返す**: 利用不可・ネットワーク・作成の拒否（429 を含む）・期限・予期しない終了。文言は呼び出し側が分類ごとに固定で持ち、`cloudflared` の生の出力は載せない。ログへ出す文字列は `*.trycloudflare.com` をマスクする（URL が共有そのものであるため）。作成の拒否は自動で再試行しない

## ゲート

`cloudflared` の向き先は、開始のたびに `127.0.0.1` の一時ポート（`listen(0)`）へ立てるゲートだけにする。固定のポート範囲を予約しないのは、別のプロセスやサンドボックスから到達できる範囲と衝突させないため。ゲートは要求ごとに次の順で判定し、通った要求だけを既存の `service-proxy` でサンドボックスの 8080 へ流す。

1. 期限切れは 410。終了はタイマーが行うが、その遅れに備えて要求のたびにも確かめる
2. 公開しているアプリの同一性（下の表）。判定は `ServeService.runtimeStatus()` の結果だけを使い、状態は持たない
3. プロキシへ転送する。`Location` の書き換え先は、起動後に確定する共有 URL の origin にする

| 現在の状態 | 動作 |
| --- | --- |
| 到達不可 | 通す（プロキシが 502 を返す。束縛は変えない） |
| `generation` が束縛と同じ | 通す |
| `generation` が違い、束縛に起動元の会話が無い | 403 を返し、共有を終える（理由 `replaced`） |
| `generation` が違い、起動元の会話と `cwd` が束縛と同じ | 束縛の `generation` と対象を更新して通す |
| `generation` が違い、起動元の会話か `cwd` が違う | 403 を返し、共有を終える（理由 `replaced`） |
| `generation` が違い、起動元が分からない（記録と待受が一致しない） | 通さず 503 と `Retry-After`。確認待ちに入る |
| 状態を取れない | 503 と `Retry-After`。共有は終えない |

- 確認待ち: `serve` の起動し直しの途中や、待受だけが入れ替わったときに、正当な起動し直しの共有を終えないための猶予。`serve` の起動の期限より長い時間を置き、その間は通さない（何も公開されない）。満了時に状態を取り直し、同じ会話・同じ `cwd` なら再束縛して戻る。別のアプリが待受していれば（待受だけの入れ替わりを含む）共有を終える。到達不可なら待ちを解いて束縛を変えない。状態を取れないときは終えずに猶予を置き直す。猶予の間に別の会話が待受を取ったら、要求の時点で終える
- タブを閉じるなどで要求が来なくなっても、猶予のタイマーは 1 本だけ持ち、満了で決める。再束縛・終了・停止で捨てる
- 403 / 410 / 503 の本文は短い固定文言の `text/plain` にし、アプリの内容・内部のホスト名・`cloudflared` の出力を載せない。応答には `X-Robots-Tag: noindex` を足す（アプリが付けていなければ）
- 置き換えの終了は、応答を返した後に非同期で起こす（ハンドラの中でゲートの close を待たない）。同時に来た要求が終了を起こしても 1 回だけ
- 判定は `ServeService` の状態のキャッシュ（最大 2 秒）を使う。並行した要求は進行中の 1 回の確認を共有し、ページ表示のバーストで確認を重ねない
- WebSocket と SSE は扱わない。upgrade は落ちるだけで安全側に倒れ、ゲートへの適用は `main` の変更を基準に別途行う（詳細は [#2804](https://github.com/u7chan/monorepo/issues/2804)）

## DNS の確認

`/ready` が 200 でも、公開ホスト名がまだ引けるとは限らない。スパイクでは、`ready` の約 6〜7 秒後に DoH で A レコードが見え、その前にシステムのリゾルバで引くと NXDOMAIN が約 30 秒キャッシュされた。そのため `start` は、利用者へ URL を見せて `active` にする前に、公開ホスト名の A レコードを DoH（`cloudflare-dns.com` の `443`）で確かめ、見えてから短く待つ。システムのリゾルバでは先に引かない。

- 確認には `ready` とは別の上限を置く。上限までに見つからない（A レコードが無い・DoH に届かない）ときは開始の失敗として片付け、URL を出さない
- 確認は中断できる。`stop` / `shutdown` で開始を止めたときは、確認の完了を待たない
- 問い合わせはテストで差し替えられる形にし、テストは実ネットワークを使わない

## 状態と API

状態は BFF のメモリだけに持ち、DB・設定・資格情報を持たない。同時に共有できるのは 1 本で、BFF が止まればトンネルも消える。開始・停止は `ServeService` とは別の論理ロックで直列化する。`stop` は開始のロックに並ばず、`start` の最中でも起動基盤の `stop()` で待ちを中断する。開始を呼んだ HTTP の要求が切れても開始は止めない（止めるのは明示の `stop` だけ）。

| メソッド | パス | 契約 |
| --- | --- | --- |
| GET | `/api/serve/tunnel` | 200 で状態。起動基盤を使えないときも 200 で `available: false` と理由 |
| POST | `/api/serve/tunnel/start` | `{ generation, ttlMinutes }` を必須にし、`active` を返す。同期で、起動基盤の期限と DNS 確認の上限の合計まで |
| POST | `/api/serve/tunnel/stop` | 冪等に `idle` を返す |

- DTO は `{ available, unavailableReason, state, provider, active, lastEnded }`。`active` は `{ url, startedAt, expiresAt, target }` で、`target` は起動元の会話名・`cwd`・起動コマンドを再束縛のたびに更新する。起動元の会話が分からず記録だけ一致するときは `title` だけ `null`、記録も分からないときはすべて `null`
- `lastEnded` は直近の終了（理由と時刻）で、次の開始まで持つ。`message` は起動の失敗のときだけ、分類に応じた固定文言を載せる（理由ごとの文言はこの層が持ち、GUI は写さない）。開始の失敗の応答の文言は、この `message` と同じにする（GUI は、同じ失敗を応答と終了の通知で二重に出さないために、文言の一致で見分ける）
- 開始の失敗は 400（本文・期限の値）、409（サービスが稼働していない / `generation` の不一致 / すでに共有中）、502（サービスの状態の確認・起動・DNS 確認の失敗。分類ごとの固定文言）、503（サンドボックス未設定・起動基盤が使えない）。`cloudflared` の出力も、サンドボックスの例外の生の文言も載せない
- 応答は失敗も含めて `Cache-Control: no-store`（`url` が共有そのもの）。ログにも URL を出さず、開始・終了と理由だけを残す
- POST の 2 本にだけ `sameOriginOnlyGuard` を掛け、GET は掛けない。平文 HTTP の LAN 配備ではブラウザが GET へ `Origin` も `Sec-Fetch-Site` も付けず、掛けると状態を読めない。共有 URL はアプリにも届くので、GET を絞っても守れる範囲はほとんど変わらない。このガードは認証ではなく、サンドボックスから BFF に届く配備では叩ける（Git 設定 API と同じ既知の制限）

## 画面

入口・ダイアログ・共有中の表示・終了の通知の契約。描画は `client/src/components/ServeShareDialog.tsx`・`client/src/components/ServedAppStatus.tsx`・`client/src/components/RuntimeServiceCard.tsx`、取得は `client/src/hooks/useServeTunnel.ts` が持つ。受入は [testing.md](testing.md#一時共有の受入)。

### 入口と共有中の表示

- 入口は 2 か所: 設定 → ランタイム（`/settings/runtime`）のサービスの稼働中カードと、チャット。ランタイムは誰が起動したアプリでも対象にし、確認に起動元・作業ディレクトリ・起動コマンドを出す（起動元が分からなければ不明と出す）。チャットは、この会話が起動したアプリだけを対象にする。他の会話・起動元不明のアプリは、ランタイムの入口から共有する
- **共有中（準備中を含む）の表示と停止は、サービスの状態にも、サービスの状態の取得の失敗にも関係なく出す**。共有はサービスが止まっても期限まで続く（ゲートは到達不可でも共有を終えず、訪問者には 502 が返る）ので、止めた途端に表示と停止が消えると、消し忘れを防げない。ランタイムではカードの共有の区画（サービスの到達可否の分岐の外）に、チャットではバッジ（desktop は右寄せクラスタ左端のグループ、singleColumn は状態アイコンのメニュー）に出す
- **共有中の表示は、全会話のチャットに出す**。公開枠も共有も BFF で 1 本の全体の状態で、共有を始めた会話を DTO に持たせない（サービスの他の会話・起動元不明の表示と同じ扱い）
- 共有中の表示は、押すとダイアログを開く。desktop のグループは右寄せクラスタの左端に置き、出入りで通知・作業環境の位置を動かさない
- 利用不可は、入口を出したまま押せなくして、サーバーの理由を出す

### ダイアログ

1 つのダイアログが、確認・準備中・共有中を、サーバーの状態から描き分ける。ダイアログに独自の進行状態を持たないので、閉じても開き直しても、別の端末で始めた共有でも、同じ表示になる。

- **確認**: 対象・期限・畳んだ注意を出す。初期焦点は取り消し側に置き、開いたときの Enter で公開させない。共有の有無が切り替わったとき（開始・準備中の失敗・期限切れ・外からの停止）も、焦点を取り消し / 閉じる側へ戻す。確認は、見せた時点の対象と世代で行う。開いている間にポーリングで対象が変わっても、見せた内容を黙って差し替えず、食い違いを示して開始を止める（最新の内容で確認し直すまで、確認していないアプリを共有させない）。開始が 409 で断られたときも、最新の対象で確認をやり直す。開始の失敗はサーバーの固定文言をダイアログ内に出し、同じ操作で再試行できる（自動で再試行しない）
- **準備中**: 進行を示し、開始を中断できる。開始の最中の停止は開始の中断で、その開始の応答は失敗として見せない
- **共有中**: QR・URL・開く・コピー・残り時間・対象・停止。停止に確認は挟まない（止める操作は安全で冪等）
- Escape と閉じるは閉じるだけで、共有を止めない。閉じても共有が続くことを文言で示す。取得に失敗していても、最後に分かっていた共有の停止は押せる

QR の描画・URL のテキスト・開く・コピーは `client/src/components/QrCodeView.tsx` が持ち、共有物の QR ダイアログと同じ契約（白地と黒の固定色・規格の余白・SVG・URL の併置）を守る。QR を共有の唯一の経路にしない（[static-sharing-design.md](static-sharing-design.md)）。

### 状態の取得

- 共有はサービスの稼働と独立に続くので、サービスの状態には条件づけず、画面を開いている間（チャットは会話を開いている間、設定 → ランタイムは画面を開いている間）、サービスの状態と同じ周期で取る
- 取得を省く条件は、周期の hook（`client/src/hooks/useRuntimePolling.ts`）には持たせない。ランタイムとデバッグの serve も使う共有の hook に止める仕組みを足すと、影響が広い。コントローラーが、利用不可が確定していて共有も無い間は（取得しても変わらないので）取得を省き、直前の状態をそのまま残す。設定 → ランタイムの再読み込み 1 回で、チャットの入口を含む、開いている取得の全部が再開する
- 開始・停止の応答は状態として適用し、先に発行した取得の遅い応答で上書きしない。取得に失敗しても、最後に取得できた状態を残して共有中の表示と停止を消さない
- 残り時間は、期限と手元の時計の差を分単位で出す。時計は注入できる形にする

### 終了の通知

`lastEnded` はサーバーに次の開始まで残るので、画面側が「いつ見たか」で出し分ける。

- 出すのは、このタブが最初の取得で見た終了より新しい終了だけ。最初の取得に残っていた古い終了（数時間後に開いた別のタブなど）は出さない。新しさはサーバーの時刻同士で比べ、端末の時計のずれを持ち込まない
- 同じ終了は、タブの中で 1 回だけ出し、閉じられる。入口が 2 か所でも別々に数えない。通知の台帳はページの生存期間で 1 つ持つ（スペース切替で画面が作り直されても保つ）
- 利用者の停止は出さない。新しい共有が始まったら、前の終了の通知は消す
- 文言の持ち主: 開始の失敗はサーバーの固定文言をそのまま、期限切れ・置き換え・予期しない終了はクライアントの固定文言（正は `client/src/lib/serveTunnel.ts`）。ダイアログが同じ開始の失敗を表示中なら、通知として重ねない

## 版の更新

版と sha256（linux の amd64 / arm64）は配布スクリプト `scripts/install-cloudflared.mjs` の定数で、更新は手動（Dependabot の対象外）。`cloudflared` のサポートは直近 1 年の版に限られるので、定期的に上げる。

1. 新しい版のリリース asset の sha256 を、amd64 と arm64 の両方で取り直し、定数を更新する
2. 固定した版の `tunnel --help` で、起動の引数が通ることを確かめる（フラグの位置と、`--protocol` の有無は版で変わり得る）
3. 実機で 1 回起動して、`/quicktunnel` と `/ready` の応答の形と、起動ログの文言を確かめ、テストの fixture（`server/test/fixtures/cloudflared-output.ts`）を実物の出力から取り直す。ホスト名・IP・ID・拠点は架空の値へ置き換える
4. イメージは、ビルドで sha256 の照合と `--version` の実行が通ることを確かめる

## 採らなかった案

- **`PATH` の探索**: エージェントが書ける場所のバイナリを拾い、BFF がサンドボックスの外で起動することになる
- **BFF の env の継承**: LLM のキーと master key が子へ渡る。許可リストにする
- **`--pidfile` への依存**: 最初の接続のあとにしか書かれないので、起動中の中断や、起動の途中で BFF が落ちたときの子を扱えない。BFF 自身が書く記録を正にする
- **ログ解析だけの URL 取得**: ログの文言は版で変わる。`/quicktunnel` を正にし、ログに頼るのは URL の代替取得と失敗の分類だけにする
- **書き込める場所への設定ファイル**: ingress が `--url` より優先され、向き先を差し替えられる。空の設定を渡す
- **公式の Docker イメージからの COPY**: arm64 への対応と、distroless のバイナリが trixie で動くかが未確認で、版を dev の導入スクリプトと 2 か所で持つことになる。リリースの asset を sha256 で固定して取得する
- **異常終了した `cloudflared` の自動再起動**: `serve` と同じく、自動復旧は持たない
- **アクセスコード / Cookie のゲート**: URL は Quick Tunnel が共有のたびに変わるため、前の受取人の URL が次の共有で通ることはない。確認画面で「URL を知っていれば期限まで誰でも開ける」ことを示す
- **ngrok を先に実装する**: 無料プランは dev ドメインが 1 つで URL が毎回同じ、リクエスト数と転送量の上限、初回の警告画面がある。未バンドルの開発サーバーは 1 画面で多数のリクエストを出すため上限に当たりやすく、共有ごとの秘密にもならない
- **トンネルの状態の永続化・BFF 再起動後の復元**: 状態はメモリだけに持つ。再起動で共有は終わり、残った子は次の起動の掃除が止める
- **要求ごとの `fresh` な状態確認**: ページ表示のバーストでサンドボックスへの確認が並行して走る。状態のキャッシュ（最大 2 秒）を使う
- **`ServeService` の内部へ結合して束縛を読む**: `runtimeStatus()` の公開契約だけを使い、ゲートと状態を fake に差し替えられる形にする
- **GET への `sameOriginOnlyGuard`**: 平文 HTTP の LAN 配備で状態を読めなくなり、守れる範囲も増えない
- **`owner` が null になった時点で即座に終了する**: `serve` の起動し直しの途中の中間状態で、正当な起動し直しの共有が終わる
- **DNS を確認せずに `active` にする**: `ready` の後も数秒は名前が引けず、早く引くと NXDOMAIN が約 30 秒キャッシュされる
- **確認できないまま `active` にして警告を出す**: 「未確認」の状態が DTO と画面に増える
- **共有中の表示をサービスの状態に条件づける**: サービスが止まった途端に表示と停止が消え、期限まで続く共有を消し忘れる
- **共有を始めた会話の画面だけに共有中を出す**: 共有は BFF で 1 本の全体の状態で、会話を DTO に持たせる必要が出る
- **確認の内容をポーリングで更新し続ける**: 読んでいる最中に対象が入れ替わり、確認していないアプリを共有してしまう
- **終了の通知を、サーバーの既読で管理する**: DTO に既読と閲覧者の概念が増える。タブ単位の台帳で足りる
- **OS の共有シート（`navigator.share`）**: セキュアコンテキストが要り、LAN の平文 HTTP では使えない

## 既知の制限

- 起動時刻を確定できなかった記録は、自動では回収しない。`spawn` の直後に BFF が落ちた場合などで、記録と `HOME` が残る。
- 配布のロックは、持ち主の pid と起動時刻で生存を見る。持ち主の判定から新しいロックを取るまでの間に、別の取得者が古いロックを外す競合が残る（同時実行は `pnpm dev` の二重起動程度で、失敗した側は再実行で回復する）。`.install.lock` が FIFO だと読み取りが返らず、待ちの上限も効かない。配置先にそれを置ける状況は、既にバイナリを差し替えられる状況なので想定しない。
- 起動元の確認は flock が前提。flock を持てないファイルシステム（一部の NFS など）や、`node:ffi` の無いビルドでは起動できない（`lock_unavailable`）。
- 孤児の掃除は best-effort で、Linux の `/proc` と pidfd が前提。記録を書く前に BFF が SIGKILL された場合と、実体のバイナリを差し替えたあとの古い子は、掃除できない。pidfd は Node の `node:ffi` で開く。FFI の無いビルド（`--no-experimental-ffi`、非公式ビルド）では起動元のロックも取れないため起動しない（数値の pid へは落とさない）。掃除に失敗したときは起動ログに `could not stop` として出る
- 作成は、短時間に多数だと 429 で拒否される。上限も回復時間も公開されていない。作成と停止の繰り返しを前提にしない
- 外向きに 7844 の TCP / UDP と、`api.trycloudflare.com` の 443 が要る。7844 に届かないときは、QUIC から HTTP/2 への切り替えが続き、ネットワークの失敗ではなく期限切れに見える可能性がある（未確認）。HTTP プロキシ経由の環境は想定しない（env を渡さないため）
- エージェントが書ける場所の判定は、Landlock の固定の書き込み先・ワークスペースの root・共通スキルの root に限り、起動のたび・配置のたびの時点のもの。判定のあとに書き込み先が差し替えられる場合は守れない。それ以外の場所をエージェントが書ける構成は想定しない
- 起動のロックは通常ファイルを前提にする（FIFO や symlink は開かない）。配置先にそれらを置ける状況は、既にバイナリを差し替えられる状況なので想定しない。NFS 上の flock は保証しない
- 画面の残り時間は手元の時計との差で出すので、端末の時計がずれると表示がずれる（共有の終了はサーバーが決めるので、表示のずれが終了に影響しない）
- 確認画面の注意の WebSocket の記述は、ゲートへの WebSocket の転送（`#2808`）を適用したら書き換える
- BFF の再起動で終了の記録も消えるので、再起動で終わった共有の通知は出ない（見ていたタブでは、共有中の表示が消えるだけ）
- `PI_CLOUDFLARED_PATH` は、利用者が指す任意のバイナリを実行する。BFF の設定（env）を書ける人は、もともと BFF の実行内容を決められる前提とする
