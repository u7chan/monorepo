# ファイルのアップロード（設定のファイル画面のドラッグ＆ドロップ）

設定 → ファイル（`/settings/files`）のファイルツリーへ、PC のブラウザーから OS のファイルをドラッグ＆ドロップしてワークスペースへ保存する。口としての API 契約は [api.md](api.md#アップロード)、保存名の検証・連番・実書き込みはサンドボックスが持つ（[sandbox-api.md](sandbox-api.md#post-v1filesupload)）。

## 入口と範囲

- 対象は設定 → ファイル（`/settings/files`）の「ファイルツリー」タブだけ。「ダウンロードの除外」タブとチャット右パネルの作業環境はドロップ先にしない
- 保存先は**その面の root（常にワークスペース root）の直下**。ツリーのフォルダ行へ落として配下へ入れる操作は持たない
- ファイルを掴んで面の上に来た間だけ、面全体に破線のドロップゾーンを重ねる。`dragenter` / `dragleave` を数えて子要素のまたぎで消えたり点滅したりしないようにし、`dragend` / 面の外の `drop` / `blur` / `Escape` で閉じる
- 対象は `dataTransfer.types` に `Files` を含むドラッグだけ。ツリーの行を入力欄へ運ぶ社内の参照ドラッグ（独自 MIME）は通さない
- OS のフォルダをドロップして配下を一括で上げる操作は持たない（1 回のドロップはファイル単位）
- モバイル（タッチ）は対象外。タッチには drag イベントが無く、別の入口（ファイル選択など）を足していない。キーボードだけで完結する入口も持たない

## 上限

| 上限 | 値 | 決め方 |
| --- | --- | --- |
| 1 回のドロップの件数 | 10 件 | チャットの添付（`MAX_ATTACHMENTS`）と同じ値に揃え、1 回の操作で一覧と状態表示が読み切れる量にする。11 件目以降は保存せず、理由を行に残す |
| 1 ファイルのサイズ | 100 MiB | サンドボックスの `SANDBOX_MAX_UPLOAD_BYTES` と同じ値。BFF は宣言された `Content-Length` で先に止め、実際の受信バイトはサンドボックスが数える |
| 同時に送る本数 | 3 本 | 回線・サンドボックスの書き込み・一覧の再取得を飽和させず、細い回線でも完了までの待ちを短くする |

サイズ超過は件数の枠を消費しない（10 件の枠は「保存を試すファイル」に使う）。上限内でも保存名が既存と衝突した場合は上書きせず、サンドボックスが `name-1.ext` の連番で保存する。**失敗したファイルがあっても、同時に成功したファイルは残す**（バッチ全体のロールバックはしない）。

## 進行と結果

`client/src/hooks/useWorkspaceUploads.ts` が 1 本のキューを持ち、`client/src/lib/fileUpload.ts` の `UPLOAD_CONCURRENCY` を超えないように送る。待機中に別のドロップが足されても同じキューへ積むため、同時数はバッチをまたいで一定になる。

- 状態はファイルごとに `queued` / `uploading` / `done` / `error` を持ち、面の上に進行と結果を出す（エラーがあるときは `role="alert"`、無いときは `role="status"`）
- 失敗（上限超過・API のエラー）はファイル名と理由を残し、閉じるまで消さない。成功だけのときは件数を出し、閉じる導線を出す
- 同名で連番になったファイルは、要求名と一覧の行名が違う理由を結果に出す
- 一覧の再取得は、キューが空になったときに成功が 1 件以上ある場合だけ 1 回行う。1 ファイルごとに再取得するとツリーが点滅し、コストも件数に比例するため
- 一覧の取得が進行中の間に再取得の要求が来た場合は、その取得が決着してから 1 回だけ取り直す。取得中にその場で状態を捨てると、後から届く古い応答が取得済みとして適用され、アップロード後の行が手動の再読み込みまで現れないため
- ページを離れると実行中の要求は中断する（サンドボックスの temp は失敗時と同じ経路で片付く）

## 採用しなかった案

- **フォルダ行へのドロップで配下へ保存**: 保存先を選べる点は便利だが、ドラッグ中の行ハイライトと、既存の参照ドラッグ（行 → 入力欄）との競合を別途設計する必要がある。現行は root 直下だけにし、必要になったら保存先を選ぶ操作として足す
- **進捗率の表示**: `fetch` では送信バイトの進捗が取れない。`XMLHttpRequest` を別経路で持つほどの価値が無いため、待機 / 送信中 / 完了の 3 状態にする
- **失敗したファイルの自動リトライ**: 理由（サイズ・権限・通信）によって可否が変わる。同じ内容を黙って再送せず、利用者がドロップし直す
