# 静的コンテンツ共有

エージェントが会話の中で生成・ビルドした静的成果物を Cloudflare へ公開し、共有 URL を管理する機能。`serve`（サービス）とは別機能として扱う。

このファイルは機能の概要・画面（共有ダイアログ / 接続 / 管理一覧）・既知の制限を持つ。実装より先に決めた設計判断と採用しなかった案は [static-sharing-design.md](static-sharing-design.md)、HTTP 契約は [static-sharing-api.md](static-sharing-api.md) を正とする。状態・列・上限値の正は実装とテスト（[persistence.md](persistence.md#アプリデータsqlite)）。

## 責務の分離

| | `serve`（サービス） | 静的コンテンツ共有 |
| --- | --- | --- |
| 対象 | サンドボックスの `:8080` で動くアプリ（動的も可） | ビルド済みの静的成果物だけ |
| 公開先 | BFF 経由の一時プレビュー | Cloudflare（workers.dev） |
| 寿命 | プロセスが動いている間 | 停止・削除するまで |
| URL | アプリを開いている間だけ有効 | 外部へ配れる安定 URL |
| 起動 | コマンドを実行する | 実行しない（成果物を置くだけ） |

`ServeService` / `serve` tool と実装・状態を共有しない。共有は「ビルド済みディレクトリをスナップショットとして置く」だけで、
ビルドやサーバー起動は行わない（ビルドはエージェントが既存の bash で行う）。

## 全体の流れ

```text
セッション（作業ディレクトリ）
  │ エージェントが HTML / CSS / JS を生成し、必要なら pnpm build
  ▼
source_path（例 dist/）
  │ BFF がサンドボックスから ZIP で取得して検証
  ▼
BFF（Cloudflare 資格情報はここだけ）
  │ manifest 登録 → アセット送信 → version / deployment
  ▼
Cloudflare Workers（workers.dev）
  ▼
公開 URL
```

## GUI（共有ダイアログ）

手動で公開する最小の導線。取り消しにくい確認と結果だけを 1 つのダイアログに閉じ、確認と一覧はタブで分ける。

- **入口はチャット右パネル（作業フォルダ面）の行の ⋯ の「共有」だけ**。ディレクトリ行はそのディレクトリ、作業フォルダ直下（ツリーの root）の `index.html` 行は「このフォルダを共有」で作業フォルダ全体を対象にする。`compact` では同じ中身が全画面のシートで開くため入口は増やさない（ツールバーにも第 2 入口を置かない）。**設定 → ファイル（`/settings/files`）には出さない**（共有 API の `directory` はセッションの作業フォルダ相対で、共有物も `sessionId` を持つため）。会話が決まっていない面（プロジェクト起点の新規会話 / スキル面 / 読み取り専用の面）も出さない。symlink の行にも出さない
- **公開元の会話か、同じ作業フォルダを共有する会話が実行中（実行 / キュー待ち / 圧縮中）の間は共有できない。** プロジェクト会話は全セッションが同じ `projectCwd` を共有するので、自分の会話が idle でも兄弟会話が `dist/` を書き換えていることがある。取得する ZIP は live なディレクトリなので、書き換えの途中で公開すると「`index.html` は新版で資産は旧版」「書きかけのファイル」のような半端なスナップショットが外部公開 URL に載り得る。行の ⋯ の「共有」は項目を消さず、理由（自分が実行中なら `SHARE_RUNNING_NOTE`、兄弟会話なら `SHARE_WORKDIR_RUNNING_NOTE`）を 2 行目に出して押せなくし、run が終われば押せるようになる。ダイアログを開いた後に run が始まったときは、主操作（更新する / 共有する）と副次の「新しく共有」を同じ理由で無効にする。設定 → 共有の「更新」と「公開を再試行」も同じ条件で無効にし、理由は `SHARED_CONTENT_UPDATE_RUNNING_NOTE`。条件は BFF の 409 と揃える（`sessionBusy` / `workdirBusyKind`。画面ごとに集合を書かない）。ただし画面の先回りは会話一覧の `projectId` で兄弟を探すため、**プロジェクト登録を解除した会話（`projectCwd` は残り `projectId` が消える）では兄弟を見つけられず、押した時点で BFF の 409 になる**（判定の正は cwd を見る BFF）。**プレビューは補助なので塞がない**（見え方はその時点のもの、という既存の契約どおり）
- **作業フォルダ自身の入口は非プロジェクト会話だけ**（`SessionSummary.projectSession` が明示的な false のときだけ出す。true / 未指定 / 会話が未確定は出さない側へ倒す）。**ディレクトリ行の「共有」はセッション種別で制限しない**（プロジェクト会話でも従来どおり使える）。サブディレクトリの `index.html` 行には出さない（そのディレクトリ行の「共有」で足りる）
- **ダイアログは「公開」と「共有物」の 2 タブ。** 初期は「公開」で、公開対象・表示名・プレビュー・注意・結果を置く。「共有物」はこの会話の共有物の一覧だけを持ち、ラベルに件数を添える。タブはダイアログのローカル状態で、URL には載せない（開閉で捨てる状態しか持たない。設定 → 各セクションのタブは URL が正）。`role="tablist"` / `role="tab"` / `aria-selected` だけを使い、`aria-controls` と矢印キーは持たない（設定 → モデル → プロバイダー詳細の認証方法のタブと同じ水準）
- **キャンセル / 主操作 はタブの外の固定フッターに置き、両タブで同じ位置に出す。** 主操作は同じ公開元の共有物があるかで「更新する」と「共有する」を切り替える。「共有物」から確定したときは「公開」タブへ戻して実行し、結果もそこで出す。受付の後（結果を出している間）はフッターを出さず、「公開」タブへ固定して「共有物」を選べなくする（結果と一覧の導線を混ぜない）。スクロールは本文だけが持ち、ヘッダ・タブ・フッターは動かさない
- **主操作は同じ公開元の共有物があるかで切り替える。** 判定はプレビューの `sourcePath` と一覧の `sourcePath` の文字列比較で行う（`directory` の字面で比べない。`.` / `./` の解決規則はサーバー側にある）。既存があれば主操作は「更新する」で、押すと `POST /api/shared-contents/:id/publish` を呼び、**新しい URL を作らずに同じ URL へ成果物を上げ直す**。既存が無ければ今までどおり「共有する」で新規作成。更新の対象があるときは副次に「新しく共有」を置き、**押したときだけ** `POST /api/shared-contents` を呼ぶ（重複の作成はサーバーが拒否しないので、押し間違いを主操作の配置で減らす）。副次の直前には「新しい URL が増えます」と 1 行添える（Worker が 1 つ増えるため）。**同じ公開元が `publishing` の間は主操作を出さず**、「公開処理中です」と理由だけを出す（閉じて開き直して `activeId` が失われても、Worker と URL を二重に作らない。下記の「共有物」タブの項も同じ規則）
- **更新では、押す前に「何を更新するか」と「何が起きるか」を出す。** 状態別の文言（生きた / 停止中 / 未デプロイまたは `failed`）と表示名を変えられないことの文面は `client/src/lib/sharedContents.ts` の `shareUpdateNote` などが正で、ここには写さない。契約として残すのは次の 3 点。**更新先の URL は記録があれば確認画面に出す**（URL は受付時に確定しているので、新規と違って押す前に示せる）。**更新では表示名を変えられない**（更新の入力は成果物だけで、改名は 設定 → 共有 の ⋯ に分ける）。**未デプロイ・`failed` からの復帰も更新の同じ経路**で、成果物を上げ直して新しい deployment を積む（版を戻さない再公開とは別の操作）
- 「公開」タブは 確認 → 受付 → 状態 → 結果 を 1 面に出す。確認には 公開対象の path（作業フォルダ相対）、外部から誰でも見られること、静的ファイルに含めた秘密値も公開されること、この公開ダイアログからは停止・削除ができないことを出す。**新規作成の確認画面には最終 URL を出さない**（URL は受付時に確定するため、公開前にはクライアントから決められない）。**この「確定 URL を出さない」は新規作成だけの条件で、更新は既に決まっている URL を更新先として確認画面に出す**（どちらの経路でも、確認画面には「開く」「QR コード」「URL をコピー」を出さない。未デプロイの行では押しても 404 になる）。表示名は任意の入力欄（最大 100 文字）で、既定はセッションタイトル。空欄で送ると API がディレクトリ名（root ではセッション ID）へ落とす。**表示名は URL を変えない**（URL は script 名 = 共有物 id 由来）ことを確認画面に書く。**注意の 4 行は既定で畳む**（`client/src/components/CollapsibleNotice.tsx`）。summary は畳んだままでも要点（誰でも見られること・秘密の値も公開されること）が読める 1 行にし、4 行は展開で読める。注意の文面は経路で入れ替える（新規は確定 URL を出さないことを含む `SHARE_CONFIRM_NOTES`、更新は URL が変わらないことを含む `SHARE_UPDATE_CONFIRM_NOTES`。文言と並びの正は `client/src/lib/sharedContents.ts`）
- **プレビューが失敗して `sourcePath` が分からないときは、更新の対象を特定できないので新規のみにする。** 同じフォルダの共有物が既にあっても「共有済み」と言い切らず（存在を確認できていない）、「同じフォルダの共有物がある場合、更新は 設定 → 共有 から行えます」と断定しない案内だけを出す。プレビューが成功しても同じ公開元が無ければ何も出さない
- **プレビューは補助で、公開されるものの確定は公開ジョブの検証。** ダイアログを開いた時点でプレビューを 1 回取り、件数（ディレクトリも数えるので「ファイル数」とは書かない）・合計サイズ・上位のパス・一覧の打ち切り・公開されないもの（symlink / 特殊ファイル）・`problems` を出す。一覧は行数でも絞るため、**取得の打ち切り（計画の件数上限）と表示の絞り込み（先頭 N 件）は別の注記**にし、11 件以上でも省略されたことが分かるようにする。**除外は「何件の設定か」と「実際に落ちた名前（`skipped`）」を分けて出す**（件数だけでは、設定したのに効いていない場合を見分けられない）。取得中 / 失敗 / 成功を分けて表示し、**失敗しても公開の操作は塞がない**（見え方はその時点のもので、公開直前にファイルは変わり得る）。`index.html` の不在はプレビューの `problems` にも出すが、公開の成否は公開ジョブの検証結果（`failed` + `lastError`）を固定文言としてそのまま出す
- 受付（`POST /api/shared-contents` と `POST /api/shared-contents/:id/publish` の `202`）の後は `GET /api/shared-contents/:id` を `publishing` の間だけポーリングし、その間は確定の操作を出さない。完了で URL・share id・「開く」・「QR コード」・「URL をコピー」を出す（結果の表示は新規と更新で共通）。**202 を受けた id は終端を確認するまで追跡し、一覧の取得が失敗して手元に操作前の行が残っていても詳細のポーリングを続ける**（`acceptedPublishing` / `trackAcceptedSharedContent` / `settleAcceptedDetail` / `settleAcceptedSharedContent`）。追跡は一覧の成功と、詳細で終端を確認した時点の両方で精算する（一覧が失敗し続けても要求を止められる）。詳細と一覧の要求は同じ tick で投げて互いの完了を待たない（片方の保留で他方の次 tick を止めない）。操作より前に発行した一覧 GET は、遅れて届いても受付後の状態を上書きしない（`appliedSeq` の前進）
- **QR は結果と「共有物」タブの行にも置き、開く / コピーと同じ条件（公開済みで実体のある URL）だけに出す。** 設定 → 共有のカードと同じ `client/src/components/QrCodeDialog.tsx` を共有ダイアログの上に重ねて開き、QR を閉じても共有ダイアログは閉じない。QR 自体の契約（中身・配色・余白・対象の追従）は管理一覧と同じ
- 「共有物」タブの「この会話の共有物」は `GET /api/shared-contents?sessionId=<id>` の結果だけを並べ、**読み取り専用にする**（更新・停止・再公開・削除はこのタブに置かない）。**閉じて開き直すと状態と URL が戻る**（画面は状態を持ち越さず、開くたびに一覧から復元する）。`publishing` が含まれる間は一覧もポーリングする。**公開中に閉じても公開ジョブは止まらない**（キャンセルの API は無く、202 の前の受付も中断できない）。そのため閉じる・Escape は塞がず、公開中は公開が続くことと結果の確認先（設定 → 共有）を出し、閉じたことでキャンセルされたと誤解させない。一方で、**閉じて開き直したときに同じ公開元が `publishing` の間は確認画面から再送できない**（`activeId` が失われても Worker と URL を二重に作らない）。全共有物の管理一覧は 設定 → 共有（`/settings/sharing`）が持つ
- 資格情報が未登録でもメニューは出し、受付時に BFF の固定文言（設定 → 共有 → 接続 で登録）をそのまま見せる
- Escape は共有ダイアログだけを閉じる。`compact` ではダイアログが作業環境のシートの中に開くため、`cancel` / `close` を背面のシートへ伝播させない（1 回でシートごと閉じない）
- **`serve`（サービス）との違いを文言で示す。** 共有は Cloudflare への外部公開、サービスはアプリを開いている間だけの一時プレビュー
- 失敗時も BFF が分類した固定文言（`lastError` / `error`）だけを出し、API トークン・Cloudflare の生レスポンス・内部識別子は画面へ出さない

## GUI（接続）

設定 → 共有 → 接続（`/settings/sharing/connections`）は、保存済みの資格情報が Cloudflare へ届くかを明示ボタンで確認できる。

- 確認するのは**保存済みの値だけ**。未保存の下書きは確認しない（トークンの経路を 1 本に保つ）。保存直後にも自動で走らせず、利用者が押したときだけ動かす。
- 確認は `GET /accounts/{account_id}/workers/subdomain` の 1 本だけ。公開の受付が最初に呼ぶのと同じなので、権限 / アカウント / workers.dev の失敗が同じ形で出る。副産物として workers.dev のサブドメインが分かり、公開先のドメインを公開前に見られる（script 名は共有物の id から作るので、URL 全体は公開まで確定しない）。
- 結果は保存せず、その場で見せるだけ。再読み込み後は再確認が要る。設定画面の GET は外部通信に依存させない。
- 確認の進行中も保存・削除は止めない。確認中に設定が変わったら、遅れて届いた結果だけを捨てる。公開の進行中でも確認は独立して実行できる。
- 成功文言は「公開できます」と言わない。subdomain GET は `Workers Scripts Read` でも通るため、Write（Edit）権限の有無は保証できない。
- 失敗は HTTP status を添えて切り分けられるようにする。文言は接続確認専用で、公開処理向けの文言（404 の「対象の Worker」など）を流用しない。
- ボタンの無効条件・結果の出し分け・確認時刻の整形は `client/src/lib/cloudflareSettings.ts` を正とする。API 契約は [api-sharing.md](api-sharing.md#post-apisettingscloudflarecheck)。

## GUI（管理一覧）

設定 → 共有（`/settings/sharing`）が、公開した共有物の管理一覧を持つ。同じセクションの「公開の除外」は公開対象から落とす名前、「接続」は公開先の資格情報だけを扱う。

- 一覧はカードで並べ、狭い面でも横スクロールを要求する表にしない。カードは 名前 + 状態の行（右端に ⋯）→ 公開 URL のバー → メタ情報（公開元・会話・更新 / 公開 / 停止の時刻）→ 操作行 の順に置き、操作中の状態はバッジに出す
- **公開 URL は独立したバーに置き、右端にコピーのアイコンボタンを出す**（成功でチェックへ変え、`aria-label` もコピー済みへ変える）。コピーを操作行のボタンとして並べないのは、状態ごとの主操作の幅を URL の有無で変えないため。**停止中はバーを出さず、淡色のテキストで URL だけを残す**（押しても 404 になる開く・コピーを出さない既存の契約に合わせる）
- メタ情報は ・ 区切りで 1 行にまとめる（狭い面では公開元と 1 つの時刻だけ）
- 状態ごとに受け付ける操作を変える。**操作行には状態ごとの主操作だけを並べ**、`published` は開く / QR コード / 更新、`stopped` は再公開、`failed` は公開の再試行、結果不明（`publishing` + `lastError`）は停止を出す。`publishing` は二重操作を出さず、結果不明でも停止以外は出さない。UI の出し分けは案内で、安全性の正は API の状態遷移検証
- **⋯ には名前を変更・停止・削除を入れ、先頭を名前の変更、破壊的な削除を最後にする。行に出ている操作は ⋯ に重ねない**（狭い面は主操作が開くだけなので、更新と QR も ⋯ に入る）。⋯ は名前の長さに関係なくヘッダの右端に固定し、状態が変わっても主操作の幅を動かさない。公開中は ⋯ を出さない（状態が確定してから変える）
- **QR は公開 URL をその場で渡すための補助で、共有の唯一の経路にしない。** `published` かつ公開 URL があり、実体のある（未デプロイでない）カードだけに出し、専用ダイアログに共有物名・QR・URL・開く・コピーを併置する。QR の中身は公開 URL だけ（トークン・共有 / 会話 ID は入れない）、白地 + 黒の固定配色で四周に 4 モジュールの余白を取る。描画は SVG で、`data:` URL も canvas も使わず CSP の `img-src` に頼らない。表示対象は id で持ち、一覧（`contents.items`）から引き直し、状態が変わった / 消えた / URL が無くなったら閉じる。QR のための追加の取得はせず、カードと同じく一覧の更新（ポーリング / 再読み込み / 操作後の読み直し）に追随させる
- **名前の変更は表示名だけを変える。** URL・公開状態・成果物・時刻（更新 / 公開 / 停止）を変えないので、状態を問わず送れるが、画面の導線は状態が確定してから出す。空欄・未変更は送らない（[設定 → ファイル のリネーム](file-actions.md#リネーム) と同じ規則）
- **deployment が一度も成功していない行（`publishedAt` が無い `published` / `stopped`）は「要更新」として扱う。** 停止はしたが公開実績がある行とは別で、外部に実体が無いので URL・開く・コピー・停止・再公開を出さず、更新と削除だけにする。解消の経路は更新（同じ URL へ上げ直す）と削除だけで、DB の不整合行は自動移行しないため読み出し側でこの判定を持つ。`lastError` の文言では分岐せず、理由は表示だけに使う
- 更新は現在の `source_path` を再公開する。実行前に確認ダイアログで対象の path を示す。停止・再公開・削除は path を必要としない。**同じ「停止中」でも、管理一覧の「再公開」とダイアログの「更新」は別の操作**で、再公開は版を変えずに subdomain だけを戻し、更新は成果物を上げ直して新しい deployment を積む。管理一覧の `stopped` の主操作を再公開のままにするのは、一覧の操作で `source_path` を読み直す副作用を起こさないため
- 停止中も URL は残して表示し、開く・コピーは出さない。**URL を残すのは公開実績がある行だけで、未デプロイの停止中は URL を出さない**（状態表示を `status` だけで決めない）。停止は URL と記録を残す操作で、削除と違うことを文言でも示す
- 削除は確認ダイアログを出し、provider の削除が成功してから一覧から消す（BFF の 204 を待つ）
- セッションが削除された共有物も一覧に残し、その旨を示す。更新だけを無効にし、停止・再公開・削除は使える。会話一覧をまだ取得できていない間は削除済みと言い切らず、更新も無効にしない（BFF が 409 で拒否する）
- 公開元の会話が一覧に居るときは、カードに会話へのリンクを出す（通常クリックは設定を閉じてその会話へ移り、所属が別スペースならスペースを切り替えてから開く。修飾キー付きクリックはブラウザ既定の新規タブ）。会話が削除済みのときと、会話一覧をまだ取得できていない間は出さない
- 一覧全体の取得失敗と、1 件の操作失敗を分ける。前者は表示中の内容が最後に取得できたものであることをバナーで伝え、後者は該当のカードに出す。どちらも BFF の固定文言をそのまま使い、provider の生レスポンスやトークンを画面へ出さない
- `publishing` の共有物がある間は一覧をポーリングする。停止・再公開・更新・削除の応答後も一覧を読み直し、API が確定させた状態へ追随する
- **帯の右端に一括停止を置く（`/settings/sharing`）。** 対象は公開実績のある `published` と、停止だけを受け付ける結果不明（`publishing` + `lastError`）だけ。結果待ちの `publishing`・停止中・失敗・要更新は対象外（結果待ちは完了後に公開され得る）。対象は状態フィルタと連動させず全件から数え、0 件ならボタンを出さない。確認では件数・先頭数件の名前と状態・URL と記録が残ること・対象外の結果待ちを出し、一覧の取得失敗中と接続未登録では押せない
- **実行は 1 件ずつ順に行い、1 件の失敗で残りを止めない。** 実行中は一覧の操作（⋯・URL コピー・状態を変える操作）を止め、帯に完了数 / 対象数を出す。完了後に一覧を 1 回取り直し、成功・失敗・対象外を aria-live のノートにまとめる。停止は冪等なので、ページを離れて残りが止まらなかった場合は同じ操作をやり直せる
- 状態フィルタと件数、再読み込みを持つ。件数は絞り込みの外側の全件から数え、結果不明も `status` が `publishing` のままなので公開処理中として数える。**フィルタの選択肢と絞り込みは `status` のままで、公開 / 停止のチップには未デプロイ（要更新）の件数を添える**（0 件のときは出さない）。並びは状態（公開済み → 処理中 → 失敗 → 停止中）で固め、その中は更新の新しい順にする。状態フィルタは絞り込みだけで、並びの規則は変えない
- 狭い面では操作を「主操作 + ⋯」に畳み、URL コピーは URL バーのアイコンへ移す（当たり判定は 40px）。⋯ に更新 / 停止 / 削除を入れる（結果不明は停止だけ）。**未デプロイの行は主操作も⋯も更新 / 削除だけにし、セッションが削除済みなら主操作の更新を押せなくして理由を出す**（デスクトップと同じ作法）。⋯ は一覧のスクロール枠の外へ浮かせ、外側クリック・Escape・スクロールで閉じる。メタ情報は公開元と 1 つの時刻に絞る
- 空状態、一覧取得失敗、接続未登録の案内を出す。接続未登録では BFF の固定文言をそのまま出し、接続タブへの導線を添える
- `serve`（サービス）の管理とは混ぜない（同じ画面に置かず、操作も共有しない）

## 既知の制限

- URL は「知っていれば誰でも見られる」公開 URL で、認証・期限・アクセス制御は無い。秘密値を含む成果物を公開しないための注意は GUI と tool の案内で行う。
- URL は Cloudflare のアカウントサブドメインに依存する。サブドメインを変更すると既存の URL も変わる。
- アカウントの Free 枠（Worker 数）を他の用途と共有する。
- 中断した公開の復帰は subdomain の有効・無効だけを照会する。配信中の版までは照会しないため、更新の中断では新しい版が配信されている可能性がある（`published` + `lastError` で知らせる）。
- provider の状態を問い合わせできない間は `publishing` + `lastError`（停止を受け付ける）で止まる。接続が戻るまで停止も実行できないため、外部が公開中のまま残り得る。接続を復旧して停止するか、再試行する。
- 停止の結果不明で `publishing` + `lastError` になった行は、停止を再試行すれば `stopped`（公開実績あり）/ `failed`（未公開）に確定する（冪等）。停止で確定するまで削除はできない。接続が戻った時点で script が既に無ければ、停止の再試行で `stopped` + `lastError`（公開実績あり）または `failed`（未公開）に確定し、削除できる。
- 停止の応答の `status` は `stopped` とは限らない。未公開の行の停止は `failed` を返す（subdomain の無効化自体は行うが、外部に見えているものは無い）。
- 同じ共有物の更新は新しい deployment を積む。過去の deployment の掃除はしない（Cloudflare 側の保持に任せる）。
- 削除の冪等性は応答では表さない。同じ id への 2 回目は `404` で、外部で既に消えていたときの 1 回目だけが `204` になる。
- 停止した共有物の script が外部で削除されていると再公開できない（subdomain を有効にする先が無い）。その行は削除してから公開し直す。
- 公開実績の無い `stopped`（既存 DB の壊れた行など）は再公開できず、更新で公開し直す。既存の壊れた行は起動時にも自動では直さない（操作した行だけが `failed` へ収束する）。
- セッションまたはソースの作業フォルダが消えた共有物は更新できない。停止・再公開・削除だけができる。
- 公開先アカウントを変えるには、旧アカウントで既存の共有物を停止・削除する。接続を先に切り替える操作は `409` で止まる。
- 接続確認では Write（Edit）権限を確かめられない。subdomain GET は `Workers Scripts Read` でも通るため、確認できたのは「接続できた」ところまでで、公開の可否は公開時に判定する。
- 公開の除外を変えても、公開済みの共有物の配信内容は変わらない（次回の更新で反映される）。更新前に何が落ちるかは共有ダイアログのプレビューで確認する。
- 除外名はベース名の完全一致で全階層に当たるため、対象ディレクトリ自身と同じ名前の除外はその共有では無効になる（代わりに、その名前の下位ディレクトリも除外されない）。
- 作業フォルダ自身の共有はプロジェクト会話ではできない（プロジェクト全体の公開になるため）。プロジェクト会話ではディレクトリ単位で公開する。
- 作業フォルダ自身の共有は作業フォルダ全量が対象なので、エージェントが置いた調査メモや `.env` の派生名なども既定の除外に当たらなければ含まれ得る。公開前のプレビューで確認する。
- 公開はスナップショットなので、エージェントが後から `index.html` を書き換えても更新を押すまで反映されない。
- 実行中の共有は受付で断るが、**受付の直後に run が始まるケースは止めない**（公開ジョブは run の有無を見ない）。取得中にディレクトリが書き換われば半端なスナップショットは起こり得るので、壊れていたら更新で上げ直す。`ask_user` の回答待ちも `statusOf` が `running` なので共有できない（回答してから共有する）。
- **判定は公開元の作業フォルダを使う会話全体を見る。** プロジェクト会話は同じ `projectCwd` を共有するので、兄弟会話が実行中なら公開元が idle でも断る（未所属の会話は会話ごとの scratch なので、兄弟の影響を受けない。ただし分岐した会話は同じスクラッチを共有するため、未所属でも兄弟として数える。判定は cwd の一致だけを見るので、`server/src/sessions.ts` の解決を共有に広げれば自動的に効く）。逆に、セッションストアを持たない構成では未所属の会話の cwd がワークスペース root になり、どの会話が実行中でも共有が止まる（実運用の構成では起きない）。

## 実機で確認する項目

設計時点では Cloudflare のドキュメントで確認できる範囲だけを決めている。実装の最初に実アカウントで確かめ、結果をこの節へ追記する。

- `Workers Scripts: Edit`（Account スコープ）の API トークンで、Worker の作成・更新・subdomain の切り替え・削除が通る
- 静的アセットだけの Worker を API で作れる（Worker スクリプト無し。`main_module` を省略できるか）
- manifest の hash の作り方が Cloudflare の期待と一致する（Wrangler と同じ結果になるか）
- アセット送信の 1 リクエストが 100 MB を超えないよう、bucket をサイズで分割する必要があるか
- subdomain を `enabled=false` にすると外部から 404 になり、`enabled=true` で同じ URL が戻る
- `previews_enabled` を false にできる（不要な Preview URL を増やさない）
- `GET /accounts/{account_id}/workers/subdomain` でアカウントの workers.dev サブドメインを取得でき、公開 URL を受付時に確定できる
- 存在しない script の削除が 404 を返す（冪等扱いの確認）
- 残枠が無いときの API エラー（Worker 数の上限）を分類できる
- `GET /accounts/{account_id}/workers/subdomain` の応答（`result.subdomain`）と、workers.dev 未有効のアカウントでの status と `code`（空文字か 404 か）。接続確認の `no_subdomain` と 404 の文言のどちらに寄せるかを決める
- 誤ったアカウント ID で接続確認したときの status と `code`（トークン種別で 403 と 404 のどちらになるか）
